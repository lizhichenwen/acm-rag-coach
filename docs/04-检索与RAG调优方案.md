# 04 · 检索与 RAG 调优方案（v4）

> 作者：检优（向量化与检索调优专家）
> 适用版本：acm_rag_v4（题库 77 → 8000+）
> 原则：**先建基线再调参；所有阈值用分位数标定，不拍脑袋；每个改动必须能用指标证明收益。**

## 0. 现状基线与本次调优要解决的问题

### 0.1 v3 链路现状（代码定位）

| 环节 | v3 实现 | 代码位置 | 关键参数 |
|---|---|---|---|
| 查询构造 | 规则版改写：剥代码 + 补话题锚点 + 抽代码信号 | `query_builder.py` | `MAX_QUERY_CHARS=160` |
| 召回 | Chroma 单库，多路 query（主查询 + 代码信号路），每路 top-k | `rag.py:retrieve_multi` | `RAG_RECALL_K=12` |
| 融合 | 自实现 RRF | `rag.py:_rrf_fuse` | `k=60`，未加权 |
| 重排 | bge-reranker-base，缺失时降级为 `0.8·sim + 0.2·词面` | `rag.py:_rerank` | 无 top_n 截断 |
| 截断 | 距离三闸（强/弱/未收录） | `rag.py:_select_relevant` | `0.55 / 0.68 / gap 0.05 / rel 0.12` |
| 去重 | 按 title 字符串去重（RRF **之后**） | `rag.py:_dedupe_by_title` | — |

### 0.2 必须在 v4 修掉的四个结构性问题

| # | 问题 | 后果 | v4 对策 |
|---|---|---|---|
| P1 | **纯语义召回，缺 BM25 词面通道** | 题名/算法术语/英文题号（如 `CF1932F`、`LIS`、`KMP`）这类**精确匹配信号**被向量稀释，召回不稳 | 稠密 + 稀疏双路并行 → RRF |
| P2 | **RRF 在切片粒度而非题目粒度** | 一条长精讲切成 5 片全被召回时，同一题拿 5 份 RRF 分数，挤掉真正的第 2 名（长文档通胀） | 融合前**先塌缩到 problem_id**，每题每路只取最优名次 |
| P3 | **重排无 top_n 截断** | 召回多少条就重排多少条，8000 库下 recall_k 一涨延迟线性爆炸 | 重排固定 `top_n=30`，文档截断到 384 token |
| P4 | **绝对阈值 0.55/0.68 与"距离度量 + 库规模"强耦合** | 库从 77 → 8000，最近邻距离整体下移，"未收录"会被大量误判成"强相关"，幻觉率回升 | 改为**分位数标定**，并把标定指纹（库规模/模型/度量）写进配置 |

> ⚠️ **技术前提必须先纠正**：v3 用 `similarity = 1 - distance`，但 Chroma 默认 HNSW 空间是 `l2`（平方欧氏），在未归一化向量上 `1 - d` **不是余弦相似度**。v4 统一改为 **embedding 归一化 + `hnsw:space=cosine`**，此时 `sim = 1 - cos_distance` 才有物理意义，RRF/阈值才有可比性。**改度量本身就会让 0.55/0.68 失效，这正是"必须重标定"的第一个理由。**

### 0.3 v4 目标链路

```
query (含改写/代码信号)
   ├─ 稠密路：bge-small-zh-v1.5 (cosine)  → top 50
   ├─ 稀疏路：BM25 (jieba + 字段加权)      → top 50
   │        ↓ 均按 problem_id 塌缩
   └─ 加权 RRF (k=60, w_vec=1.0, w_bm25=0.8) → 候选池 60
              ↓
        cross-encoder 重排 top 30 (bge-reranker-base)
              ↓
        相关性自适应截断（分位数标定三档）
              ↓
        上下文打包（token 预算 / 同题去重 / 引用编号）
              ↓
        LLM 生成（资料不足 → 降级话术）
```

## 1. 召回层

### 1.1 Embedding 选型（v4 是否要换模型）

题库扩张后出现新语料特征：**crawled 条目约 8462 条（Codeforces ≈6000 + AtCoder ≈2500）含大量英文题名/题号/英文标签，而中文 curated 精讲仅 96 条（占 1.1%）**。两类语料语言、长度、信息密度差异极大，这直接影响模型选择与融合权重。

| 候选模型 | 维度 | 语言能力 | 512 token 上限 | 单条编码(CPU) | 8000 条内存 | 适配判断 |
|---|---|---|---|---|---|---|
| **BAAI/bge-small-zh-v1.5**（v3 在用） | 512 | 中文强，英文弱 | 是 | ~12 ms | 16 MB | ✅ 基线，保留作对照 |
| BAAI/bge-base-zh-v1.5 | 768 | 中文更强 | 是 | ~28 ms | 24 MB | ⭕ 候选，精度换时延 |
| BAAI/bge-m3 | 1024 | 中英多语 + 长文(8192) | 否 | ~60 ms | 32 MB | ⭕ 英文题名多时优先评估；可直接出 sparse 向量省掉 BM25 依赖 |
| text2vec-base-chinese | 768 | 中文中等 | 是 | ~25 ms | 24 MB | ❌ 无显著优势 |
| m3e-base | 768 | 中文强 | 是 | ~28 ms | 24 MB | ❌ 与 bge-base 同级，不必要 |

**建议**：v4 默认仍用 `bge-small-zh-v1.5`（时延最优、已私有化），在 dev 集上**必须实测对比 `bge-base-zh-v1.5` 与 `bge-m3`**。判据：Recall@10 提升 ≥ 3 个点且 P95 延迟增量 ≤ 150 ms 才换；否则维持 small。**（需实测标定）**

> 若英文元数据占比 > 40% 且 small 模型英文召回明显差，`bge-m3` 是唯一"一份模型同时出 dense+sparse"的选项，可去掉 BM25 依赖，但要注意它 1024 维 + 长文编码更慢，需压测。

### 1.2 BM25 参数

**公式（Okapi BM25，Robertson & Zaragoza, 2009）**：

```
score(D,Q) = Σ_{t∈Q} IDF(t) · f(t,D)·(k1+1) / ( f(t,D) + k1·(1 - b + b·|D|/avgdl) )
IDF(t) = ln( (N - n(t) + 0.5) / (n(t) + 0.5) + 1 )
```

| 参数 | 取值 | 理由 |
|---|---|---|
| `k1`（词频饱和） | **1.5**（网格 1.2 / 1.5 / 1.8） | 条目正文短（精讲 200–400 字，元数据条目 30–80 字），词频很快饱和；k1 过大等于"重复词刷分"。1.2–1.6 是短文档惯例区间，取中值 1.5 起步。 |
| `b`（长度归一化） | **0.75**（网格 0.5 / **0.6** / 0.75） | 长度分布已收敛：crawled **目标 160–300 字符**、curated 208–422。⚠️ 注意 **`120–300` 是质量目标（只告警不拒收）、`≤500` 才是合规硬门禁**，所以 BM25 索引里**会有少量 300–500 字符的条目**（DP/图论类摘要天然长）——这是设计如此，不是清洗不干净，不要当异常数据过滤掉。长度比约 1.9:1，接近单峰（v3 时期是 10:1 的双峰），长度归一需求减弱；`b=0.75` 仍作稳妥默认，但 **`b=0.6` 很可能更优**——**需实测**。 |
| `N / avgdl` | 运行时统计 | 每次重建索引时重算，写进索引元数据 |
| 字段权重（field boost） | **title ×3、tags ×2、正文 ×1** | 题名和标签是"精确信号最强"的字段；ACM 查询里出现题名/算法术语的概率极高，字段加权约等于人工先验，几乎零成本。（需在 dev 集验证是否保留） |
| 实现库 | `rank_bm25.BM25Okapi` 或 `bm25s`（更快） | 8000 条规模，单次查询 < 20 ms |

**索引构建注意事项**：
- 全小写；英文/数字串（`CF1932F`、`LIS`、`O(nlogn)`）作为**整体 token** 保留，不拆；
- 中文用 jieba 分词（见 1.3）；
- 停用词：中文虚词（的/了/是/在/和/吗/呢）+ 英文 the/a/is；**不要**停掉 `为什么/怎么/区别` 这类——它们对"错误类查询"是有效信号。

### 1.3 jieba vs 字 bigram

| 方案 | 优点 | 缺点 | 预期 |
|---|---|---|---|
| **jieba 分词**（主） | 术语粒度正确（`动态规划`、`完全背包`、`最长上升子序列` 是一个词，BM25 词频才有意义）；精度高 | 算法/题名 OOV 易切错（`KMP`、`01背包`、`Dijkstra`）；依赖词典 | 中文精讲查询 Recall@10 高 |
| **字 bigram**（兜底） | 对 OOV 鲁棒、零词典、无需维护 | 索引膨胀 2–3 倍；产生大量伪词（`态转`、`移方`），精度低、噪声高 | 英文/题号/生僻术语查询更稳，整体精度略低 |
| **混合（推荐）** | jieba 为主 + 自定义词典 + 英文整体 token + OOV 片段 bigram | 实现稍复杂 | 兼顾两者 |

**推荐落地**：
1. jieba + **自定义词典**（把题库 `tags`、题名、算法术语表、平台前缀如 `Codeforces` 全部 `add_word`）；
2. 英文/数字串整体成词，不进 jieba；
3. jieba 切出的**连续未登录单字**（如 `狄` `杰` `斯`）合并成 bigram 兜底。

**预期效果（需实测标定）**：在中文精讲查询子集上，jieba 相对字 bigram Recall@10 高 **3–6 个点**、Precision@5 高 **5–8 个点**；在"英文题名/题号"查询子集上两者接近或 bigram 略优。**因此不要二选一，混合最优**——这条结论本身就是论文第 5 章一个干净的实验（见 §7 E1）。

### 1.4 召回路数与 recall_k

| 参数 | v3 | v4 建议 | 依据 |
|---|---|---|---|
| 向量路 `recall_vec` | 12 | **50** | 8000 库下 12 条太窄，重排无米下锅；50 条召回延迟仅 ~10 ms |
| BM25 路 `recall_bm25` | — | **50** | 与向量路对称，RRF 融合才有意义 |
| 融合去重后候选池 | 12 | **60**（上限 100） | 两路并集 ≤100，截 60 平衡精度与重排成本；见 §7 E4 验证边际收益 |
| 最终进上下文 | 6 | **5**（长精讲）/ **6**（短条目） | 条目平均 400 token，5 条 ≈ 2000 token，符合 §5 预算 |

> 8000 条 × 512 维仅 16 MB，**暴力检索都 < 5 ms**，HNSW 不是瓶颈；若用 HNSW，建议 `M=16, ef_construction=200, ef_search=100`（召回优先）。

### 1.5 元数据过滤（domain / difficulty）的使用时机

**核心原则：默认不做硬过滤，只做软加权。**

| 场景 | 做法 | 理由 |
|---|---|---|
| 用户**未显式**提难度/领域 | 不过滤，仅在重排/截断时给 `meta` 先验加分 | 硬过滤会误杀（问"01背包"可能命中中等/困难两个层级） |
| 用户**显式**说"入门题""提高组""图论题" | 识别出 slot 后**硬过滤**（`difficulty ∈ {...}` 或 `domain == 图论`） | 意图明确，过滤缩小候选、提精度 |
| 兜底 | 硬过滤后结果为空 → **回退到不过滤** | 防"过滤过严导致 0 召回"（v3 的 `tag_filter` 已有此回退逻辑，保留） |

**三级元数据的处理方式不同（与主理人裁决一致）**：

| 层级 | 粒度 | 处理方式 | 理由 |
|---|---|---|---|
| `domain` | 一级（约 10 类） | **意图触发时硬过滤**，未触发不过滤 | 粒度粗、白名单校验成本低；但**必须意图触发**，不能每次查询都过滤——否则"这题该用 DP 还是图论"这类跨域问题会被砍掉一半候选 |
| `point` | 二级（约 75 个） | **只做软加权，绝不硬过滤** | 一题多考点是常态，硬过滤会砍掉大量正确召回；作为 `meta` 先验加分即可 |
| `difficulty_tier` | 五档 L1–L5（**由 `rating` 派生**，非独立存储） | **硬过滤用区间（±1 档），软加权用距离衰减** | 见下方"难度五档的两条用法" |

**难度五档的两条用法（派生五档 ≠ 检索精确匹配五档）**：

| 用法 | 规则 | 理由 |
|---|---|---|
| **硬过滤** | 用户说"中等题" → `tier ∈ [L2, L4]`（**±1 档区间**），**不是精确 `tier == L3`** | CF rating 是连续值离散化，1400 与 1899 同属 L3 但难度感受差很多，边界本身模糊；精确匹配会把相邻档的正确召回全砍掉 |
| **软加权** | `prior = 1 − \|tier_doc − tier_query\| / 4`（L3↔L3 = 1.0，L3↔L4 = 0.75，L1↔L5 = 0） | 比"命中/不命中"平滑，近难度题也能获得部分加分 |

**`difficulty = "未知"` 的处理**：

> ⚠️ **默认排除 unknown 是不可接受的**。依据：AtCoder **全量池** 9,900 条中仅 4,893 条有难度（47.7% 无评级）。**首批入库 2,500 条 AtCoder 的实际 unknown 占比需实测确认**（若采样时优先取有难度条目则可能远低于 47.7%），但规则必须按"保留"定——二期放开 ARC/AGC 时必然撞上。

| 场景 | 处理 |
|---|---|
| 查询**无**难度意图（绝大多数情况） | **正常参与召回**，`meta` 软加权给中性分 **0.5** |
| 查询**显式**说难度 | 硬过滤时排除 unknown；**但过滤后结果 < 3 条时自动回退包含 unknown**，并在结果标注"难度未知" |
| 引用展示 | 如实标注：`（考点提示 · 难度未知 · 动态规划/背包）` |

实现建议：过滤放在**融合之后、重排之前**（融合前过滤会让 RRF 名次失真）；难度与 `point` 更适合作为**重排后截断时的排序先验**（近分时优先匹配）。

> ⚠️ **`domain` 硬过滤的触发判据要保守，需同时满足三个条件**：
> 1. 查询中出现明确领域词（"图论""字符串""数论""动态规划"…）；
> 2. **该词不构成任何候选条目的标题主体**（如「图论基础」这类题名本身含领域词，此时不应过滤）；
> 3. **硬过滤必须放行 `domain=未分类` 的条目**。
>
> 第 3 条的依据：实测 **1,510 条（17.8%）AtCoder 条目无 domain 标签**（`未分类`）。若硬过滤时一并排除，等于**近两成语料在领域检索时永久失联**——这与 §1.5 中 `difficulty=未知` 是同一类问题：**"不知道它属于哪类"≠"它不属于这类"**。
>
> 判错的代价是漏召，远大于不过滤的代价。未触发硬过滤时，命中 `domain` 仅给 **+0.05** 软加成分；`未分类` 条目在软加权时取**中性 0.5**，不奖不罚。

## 2. 融合层

### 2.1 RRF 的 k 值

**公式（Cormack et al., 2009）**：

```
RRF(d) = Σ_i  w_i / ( k + rank_i(d) )
```

| k | 行为 | 适用 |
|---|---|---|
| 10–20 | 放大头部名次差异，top-3 之间区别明显 | 候选池很小（<30）、需要拉开头部 |
| **60**（默认） | 平滑，弱化单路名次噪声，融合稳健 | 两路各 50 条，推荐 |
| 100+ | 过度平滑，名次几乎无差别 | 不推荐 |

**结论**：`k=60` 起步（业界默认、鲁棒），dev 集上网格 `k ∈ {10, 20, 60}` 验证；若头部精度是主要矛盾再降 k。**（需实测）**

### 2.2 是否需要加权（加权 RRF）

**需要。** 两路"可信度"不同：中文语义匹配向量更强，题名/术语精确匹配 BM25 更强。不加权等于假设两路等权，会浪费信号。

**加权 RRF**：

```
score(d) = w_vec · 1/(k + rank_vec(d)) + w_bm25 · 1/(k + rank_bm25(d))
```

| 权重 | 取值 | 依据 |
|---|---|---|
| `w_vec` | **1.0**（基准） | 中文语义为主通道 |
| `w_bm25` | **0.8**（网格 0.5 / 0.8 / 1.0 / 1.2） | 题名/术语命中是强信号，但单独 BM25 精度低，故略低于向量 |
| 归一化 | 无需 | RRF 的**最大优势正是免归一化**（两路分数量纲不可比也不影响） |

> 业务域不同权重不同：若最终统计发现"用户查询里 60% 带题名/题号"，可上调 `w_bm25` 到 1.0。**禁止拍一个权重就不动，必须用 dev 集 qrels 校准。**

### 2.2.1 条目形态加权（精讲类 96 vs 考点提示 8462）

**这是 v4 特有的问题，v3 不存在**：精讲类条目（`corpus_type=curated`，含 `solution`/`concept`/`strategy` 三种形态，共 96 条，占 1.1%）vs 考点提示（`entry_type=hint`，8462 条）。同一 tag 下考点提示数量压倒性（人气 tag 可达数百条），RRF 融合后 **top-5 极可能全是考点提示**——学生看到 5 条"考点提示"却看不到唯一那条精讲，体验与正确率双输。

> **权重挂在 `corpus_type`（语料类型）而不是形态细分**，理由见下方"取舍说明"。

**三层手段，按强度递增，只上两层**：

| 手段 | 做法 | 强度 | 风险 |
|---|---|---|---|
| **A. 形态加权（默认启用）** | 融合时按 **`corpus_type`** 乘系数：`curated`=**1.15**、`crawled`=1.0 | 轻 | 权重过大时不相干精讲被挤进来 |
| **B. 形态配额（默认启用）** | 重排后若 top-5 **全为 crawled**，且存在 `score ≥ 0.6×top1` 的 curated 条目，则把它插到第 2–3 位 | 中 | 可能轻微伤 NDCG（需实测） |
| C. 档位保底 | 强相关档强制至少 1 条 curated | 重 | **破坏排序一致性，不用** |

> ⚠️ **`w_type` 挂在 `corpus_type`（两档），不是形态细分（四档）——这是有意的取舍。**
> 数据契约里 `entry_type` 有 4 个值（`solution`/`concept`/`strategy`/`hint`），理论上可给题解 1.25、知识点卡 1.15、考点提示 1.0。但**当前实现只有两档**（只对 curated 整体加权）。
> **不做的理由**：公式里写一个代码里不存在的变量，是答辩最容易被现场问穿的地方；19 条知识点卡"与题解同权"的误导风险，小于"文档与实现不一致"的答辩风险。
> **代价要承认**：curated 内部 66 题解 / 11 元知识 / 19 知识点卡 **同权 1.15**。19 条知识点卡可能被排到题解前面——这是已知损失，**写进论文"局限性"而不是假装没有**。
> **二期扩展点**：`entry_type` 4 值已在数据契约里备好，若实测证明知识点卡误导率显著（可从"引用后学生追问率"观测），只需把加权函数从 1 个字段改到 2 个字段，不改架构。

**落地参数**：`w_type(curated)` 取 **1.15**（保守值，因为 1:88 的比例悬殊，权重效应会被放大）；B 的阈值 `0.6×top1` 是初值，需实测。

**三条纪律（不遵守会毁掉消融实验）**：
1. **消融矩阵 G1–G4 必须关闭形态加权**（`TYPE_BOOST=false`）。它引入了一个与 BM25/RRF/Rerank 正交的变量，混在一起会让"G3 优于 G2"说不清是 Hybrid 还是加权。**收益单独作为 E10 报**（见 §7）。
2. 权重上调后若 **NDCG@10 下降 > 1 点**，说明压过了相关性排序，回退到 1.1 或关闭。
3. `w_type` 只在**同分/近分**时起作用才有意义；若 A 手段导致大量低分精讲进入 top-5，改用 B 手段（配额）而非继续加大权重。
4. **配额插入后，引用编号按最终展示顺序重排**，`meta` 保留 `quota_applied / original_rank / final_rank` 供调试；**前端不展示任何分数**——否则会出现"第 3 条分数比第 1 条高"的观感矛盾。

### 2.3 候选池与去重（关键改进 P2）

**融合前塌缩到题目粒度**（v3 是融合后才按 title 去重，导致长文通胀）：

```
对每一路 r：
   对每个 problem_id p：
       rank_r(p) = min{ rank_r(slice) : slice.problem_id == p }   # 只取该题最优切片名次
然后对所有 p 做 RRF
```

| 决策 | v4 规则 |
|---|---|
| 去重键 | **`problem_id`**（不是 title 字符串——`01背包` / `0-1 背包` / `01 knapsack` 是同一题） |
| 融合前 | 每题每路只计**最优名次**一次（防长文通胀） |
| 融合后 | 同题最多保留 **2 条切片**（相邻切片有上下文价值，但 >2 条纯冗余） |
| 多样性 | 同一 `tag` 最多 **2 条**（防 5 条全是"动态规划"，MMR-lite 贪心） |
| 候选池上限 | **60**（重排前） |

## 3. 重排层

### 3.1 cross-encoder 的 top_n 截断

**不截断 = 延迟随库规模爆炸**（P3）。固定截断：

| 参数 | 取值 | 依据 |
|---|---|---|
| 重排候选 `top_n` | **24**（as-built，`rerank_top_n=24`） | 24 条足以覆盖 gold（Recall@24 通常 > 0.9），再多边际收益递减；⚠️ 早期草案写 30，实现按 24 落地，以代码为准 |
| 输入截断 | 文档截到 **384 token**（query 不截） | bge-reranker 512 上限；全 512 会让长精讲重排变慢 ~30% 而增益极小 |
| batch | 16 | CPU/GPU 通用吞吐拐点 |
| 模型 | `BAAI/bge-reranker-base` | v3 已验证；base 比 large 快 2–3×，精度损失 < 1 点 |

### 3.2 延迟预算

| 环节 | CPU 预估 | GPU 预估 | 备注 |
|---|---|---|---|
| query 向量化 | 12 ms | 3 ms | |
| 向量召回 50 | 8 ms | 2 ms | |
| BM25 召回 50 | 15 ms | — | |
| RRF 融合 | 2 ms | 2 ms | |
| **重排 24 条** | **300–450 ms** | **25–50 ms** | 主要成本，故 top_n 必须截断（量级估算，需实测） |
| 截断+打包 | 5 ms | 5 ms | |
| **检索合计 P95 目标** | **≤ 700 ms** | **≤ 150 ms** | 不含 LLM 生成 |

**取舍**：重排是"精度最大、成本也最大"的一环。若线上 P95 > 800 ms，先降 `top_n` 到 16，再考虑换 `bge-reranker-v2-m3` 的 ONNX/int8 量化，最后才关重排。**关重排前必须用消融数据证明收益 < 5 个点（见 §6.4）。**

### 3.3 无模型时的降级打分公式

v3 降级是 `0.8·sim + 0.2·词面`——**权重拍脑袋、且 `sim=1-distance` 在非余弦空间无意义**。改为：

```
s_degraded = 0.55 · r_norm
           + 0.30 · cov
           + 0.15 · meta
```

| 项 | 定义 | 说明 |
|---|---|---|
| `r_norm` | **候选池内 min-max 归一化**的向量相似度：`(sim - sim_min)/(sim_max - sim_min)` | 池内归一化消除绝对分值漂移，跨查询可比 |
| `cov` | **IDF 加权词面覆盖率**：`Σ_{t∈Q} idf(t)·1[t∈D] / Σ_{t∈Q} idf(t)` | 比 v3 的等权覆盖率更合理：高频虚词命中不值钱、术语命中值钱 |
| `meta` | 先验：`0.5·1[domain匹配] + 0.5·1[difficulty匹配]`，无信号取 0.5 | 意图明确时才偏离 0.5 |

**权重依据**：主信号是语义（0.55），词面是补充（0.30），先验只做微调（0.15）——**这组权重需在 dev 集上做 3 组对比（等权 / 55-30-15 / 70-20-10）后定稿。** 降级路径的阈值必须**单独标定一套**（因为分数量纲与 cross-encoder logits 完全不同），不可复用 §4 的数值。

## 4. 截断与拒答

### 4.1 三档阈值表

> **门控分数定义（as-built，`index.py::_normalize`）**：
> ```
> similarity = max(vector_cosine, bm25_norm)
> bm25_norm  = 1 − exp(−bm25_score / 8)        # bm25_score_scale=8
> ```
> 排序由 RRF + 重排负责（两路互补），门控只需回答"**有没有任何一路 strongly 支持这条**"（OR 语义）——只取向量分会把"BM25 第 1 但余弦一般"的正确条目误杀（实测反例：「01背包内层循环为什么必须倒序」BM25#1 但 cosine≈0.78，被旧 cap=0.816 误杀，而相关性更低的 零钱兑换 以 0.936 留下）。BM25 归一化用 `1−exp(−x/scale)` 单调有界映射，**不用"除以查询理论上界"**——长查询里大量未命中词会把分母撑大。
>
> ⚠️ **两个量纲各管一段，不要混用**：三档判定（cap）作用在 `similarity`（max 融合置信度）上；肘部断层（gap）作用在重排归一化分 `score` 上。**门控不吃重排分**——bge-reranker 的 logit 是无界的、池内 min-max 后只保序不保距，不适合做绝对阈值。

| 档位 | 判据（`best` = 候选池内最大 `similarity`） | 进上下文条数 | 生成行为 | 目标指标 |
|---|---|---|---|---|
| **强相关 strong** | `best ≥ T_strong = 0.9382` | ≤5，`cap = max(T_strong, best − 0.12)` | 正常作答，逐条引用 | Precision@5 ≥ 0.85 |
| **弱相关 weak** | `0.572 ≤ best < 0.9382` | ≤2 + `weak` 标记 | 作答但声明"题库匹配度一般，供参考" | 不幻觉，标注可见 |
| **未收录 none** | `best < T_weak = 0.572` | 0 | 拒答 + 通用知识（显式标注来源） | 幻觉率 ≤ 2% |

**辅助闸门（as-built，保留 v3 的肘部思想）**：已保留 ≥2 条时，若相邻两条的重排归一化分差 `prev − cur > gap_margin = 0.05` 则截断后续——防止"第 1 名很准、第 2 名凑数"。

> 表中 `0.9382 / 0.572` 是 **2026-11-08 首轮分位数标定值**（`calibrate` 子命令，`data/reports/calibration.json` 可核）：`T_strong = 域内 p25`，`T_weak = 域外 p90 + 0.02`；域内 p10=0.837 vs 域外 p90=0.552，分离间隔 0.28。**这是"标题复读式合成查询 + 8 条生活类易负例"上的初值，不是终值**——四条局限与复核动作见 §4.1.1，dev-150 复核前不得写进论文。

#### 4.1.1 首轮标定结果（2026-11-08）与四条局限

**标定数据**（指纹 `n=8558; model=bge-small-zh-v1.5; metric=cosine`，门控关闭下测裸分——此前版本开着门标定，域外分布被截断成 0，属循环论证，已修复）：

| 组 | n | p10 | p25 | median | p90 | max |
|---|---|---|---|---|---|---|
| 域内（curated 标题 +"怎么做"） | 96 | 0.837 | **0.9382 → T_strong** | 0.984 | — | 0.9999 |
| 域外（生活类问题 8 条） | 8 | — | — | 0.384 | 0.552 → +0.02 = **T_weak=0.572** | **0.7646** |

**四条局限（按严重度排序，复核动作附后）**：

| # | 局限 | 后果 | 复核动作 |
|---|---|---|---|
| L1 | **域外样本 n=8 且全是"生活类易负例"**（红烧肉/天气/六级） | p90 在 n=8 时恰好丢掉尾部：**域外 max=0.7646 > T_weak=0.572**，至少 1/8 的域外查询会落入 weak 档被"带免责声明作答"而非拒答；且真正的拒答风险是**近失负例**（库内未覆盖的算法知识点，如线段树合并、可持久化并查集），生活类比它们好区分得多 | ① `OUT_OF_SCOPE` 扩充到 ≥40 条，其中近失算法查询 ≥20 条；② `T_weak` 改用 `max(out)+margin` 或 n≥40 后的 p95；③ 重标定后报告 false_accept_rate |
| L2 | **域内用"标题复读"式合成查询、且仅 96 条 curated** | median=0.984 说明分数被标题精确词面推高，`T_strong=p25=0.9382` 相对真实用户查询系统性偏高 → 真实流量大概率大量落入 weak（甚至 none），表现为过度拒答/满屏免责声明 | ① in-scope 加入 CF/AT 标题派生查询（96 条 curated 不代表 8558 条分布）；② dev-150（含真实会话日志）就位后按 §4.3 正式方法（precision≥0.90 的最小 t）复核并替换 |
| L3 | **`bm25_score_scale=8.0` 未进标定指纹** | 它直接决定 bm25_norm 量纲（0.9382 ↔ bm25≈22.3，0.572 ↔ ≈6.8）；若 max() 多数由 BM25 路贡献，scale 就是关键超参，语料变了不重标会静默漂移 | ① `_normalize` 加一行统计"max 由哪一路贡献"的计数日志；② scale 写入 `RAG_THRESHOLD_PROFILE` 指纹 |
| L4 | **max() 的对称误杀风险仍在**（方向反转） | 强档 `cap = max(T_strong, best−0.12)`：当 best 由 BM25 顶到 0.99 时，余弦 0.90 的语义强候选也会被 cap 砍掉 | 接受为 v1（误杀面远小于旧口径）；备选方案留作消融：none 界用 max、强档 cap 用"分路 OR"（`cosine≥T_strong ∨ bm25_norm≥T_strong`），若做则记为 E12 |

> **正面结论**：① 向量侧已确认 `hnsw:space=cosine` + `sim=1−distance` clamp 到 [0,1]，v3 的 L2 伪相似度问题已根除；② 门控关闭测裸分的修复正确，是当前标定值可信的前提；③ `max()` 的 OR 语义与"门控回答有没有一路支持"的职责匹配，认可该口径。

### 4.2 为什么 77 → 8000 必须重标定

| 原因 | 机制 | 后果 |
|---|---|---|
| **最近邻距离随 N 下移（hubness）** | 库大 100 倍，"总能找到一条更近的" | 固定 0.55 会把大量不相关文档判为"强相关" → 精度塌陷 |
| **干扰项密度上升** | 相似题的切片更多 | 单看 best score 不足以区分，必须引入 margin/重排 |
| **度量变更** | l2 → cosine（§0.2） | 数值尺度整体改变，旧常数彻底失效 |
| **模型变更** | 换 embedding/reranker | 分数分布不同，阈值不可移植 |

**结论：阈值必须绑定"库规模 + 模型版本 + 距离度量"三元组，写进配置作标定指纹；任一变化即重标定。**

### 4.3 标定方法（分位数，不拍脑袋）

**0. 标定集的构成（150 条，与 test 集严格分离）**

| 子集 | 条数 | 构成 | 用途 |
|---|---|---|---|
| **主集** | 100 | 易 50 / 中 50 | 标 `T_strong`（要 precision ≥ 0.90）、`T_weak` |
| **拒答集** | 50 | 难 40 / 超纲 10 | 标 `T_none`（要准确识别"不该答"） |
| **合计** | **150** | — | 标定专用 |

**两级降级路径（若工期不足）**：

| 方案 | 构成 | 后果 |
|---|---|---|
| 完整（默认） | 标定 150（主100+拒答50）+ test 150 = **300** | `T_strong` 由 100 条支撑，CI 约 ±6pp |
| 降级一 | 标定 100（主70+拒答30）+ test 150 = **250** | `T_strong` CI 放宽到 **±8pp**，论文须注明 |
| 降级二 | test 压到 90 = 总 150 | **只报整体指标，删全部子集结论**（CI ±10pp 无法支撑 pp 级结论） |

> ⚠️ **降级时压的是标定集，不是 test 集**——test 90 条会让所有"提升 X pp"的结论作废，而标定集压缩只是让阈值边界变抖（可通过回归护栏兜住）。

> ⚠️ **标定集 ≠ 评测集，这两份必须物理分开。** 标定集只用于确定阈值（相当于 dev），**test 150 条只跑一次、绝不参与任何调参**。若用同一份数据既标定又报指标，就是数据窥探，指标会系统性虚高（论文里会被指出）。
>
> **为什么要拆主集/拒答集**：`T_strong` 的约束是"高分档必须准"，靠的是**主集**（有正确答案的查询）；`T_none` 的约束是"低分档要敢拒"，靠的是**拒答集**（应当答不出的查询）。**两类样本回答的是两个不同问题，必须分别配比**——只有主集会把 `T_none` 标得偏松（因为看不到"该拒"的样本），只有拒答集会标得偏严（因为看不到"该答"的分布）。

1. **采样**：从 8558 条按 `domain × difficulty_tier` 双层分层抽查询源，生成 150 条标定查询（方法见 §6.1）。**主集 query 的 gold 必须在库内；拒答集 query 的 gold 必须不在库内或属超纲知识点。**
2. **打分**：对每条查询记录 `s_top`（top-1 分数）与该条是否相关（`rel ≥ 1`）。
3. **扫描阈值 t**：计算 `precision(t) = P(rel | s ≥ t)`（t 以上文档的相关比例）、以及"存在相关"分类器的 F1(t)。
4. **定强/未收录界**：
   - `T_strong` = 在主集上满足 `precision ≥ 0.90` 且样本数 ≥ 30 的最小 t；
   - `T_none` = 使"存在相关文档"判别 F1 最大的 t（等价于 Recall/Precision 平衡点）。
5. **定 weak 区间** = `[T_none, T_strong)`。
6. **冻结 + 指纹**：写入 `config`：
   ```python
   RAG_THRESHOLD_PROFILE = {
       "corpus_size": 8558, "embed": "bge-small-zh-v1.5", "space": "cosine",
       "rerank": "bge-reranker-base", "bm25_score_scale": 8.0,
       "T_strong": 0.9382, "T_weak": 0.572,
       "calibrated_on": "synthetic_title_96+8", "calibrated_at": "2026-11-08"
   }
   ```
   （示例值为 2026-11-08 首轮标定实测，dev-150 复核后替换；`bm25_score_scale` 必须进指纹——它决定 `bm25_norm` 量纲，见 §4.1.1 L3）
   启动时若 `corpus_size` 偏差 > 20% 或模型名不符，**日志 WARN 提示需重标定**。

7. **回归护栏**：每次重标定后，用固定 test 集跑一遍，`Precision@5` 与 `幻觉率` 不得回退 > 2 个点，否则回滚。

### 4.4 库规模 → 阈值/延迟 影响曲线（77 / 2000 / 8558 三档）

**这组实验要回答答辩必问的三句话**：库从 77 涨到 8000，召回会不会崩？延迟会不会炸？**为什么阈值不能写死？** 第三问只有这组数据能给出可视化证据，否则"分位数标定"只是口号。

#### 4.4.1 四档子库的构造（关键：同分布 + gold 必留）

| 档 | N | 构造方式 | 用途 |
|---|---|---|---|
| **S1** | 77 | v3 原始手工精讲库（全量） | **历史锚点**（分布不同，只作趋势起点参考） |
| **S1′** | 77 | 从 8558 按 `domain × difficulty_tier` 分层抽 77 条 | **等分布对照点**（与 S2/S3 可比，用于拟合） |
| **S2** | 2000 | 从 8558 分层抽 2000 | 中间档，看曲线形状 |
| **S3** | ≈8558 | v4 全量（curated 96 + crawled ≈8462） | 目标档 |

构造四条硬规则：
1. **gold 必留**：评测集 test 250 条 query 涉及的 gold `problem_id`（约 200 个）在抽样时**强制保留**，否则该 query 在小子库必然 miss，指标无意义。
2. **双层分层**：按 **`domain` × `difficulty_tier`** 分层（不是只按 domain），各层抽样比例 = 全库比例，偏差 < 2%。**理由：v4 语料按难度配额采样（五档实测 L1 34.9%/L2 13.0%/L3 17.6%/L4 15.4%/L5 19.1%），只按 domain 分层会导致各档难度分布漂移，曲线不可比。**
3. **三档抽样比例必须完全一致**：S1′、S2、S3 **用同一套分层比例与同一 `seed`**（`seed=20261107`）。否则 S2 若偏易、S3 偏难，曲线上的变化就分不清是"库规模效应"还是"难度分布效应"，整组实验作废。
4. **S1 与 S1′ 必须分开画**。v3 的 77 条是早期手工精讲（长、质量高、无薄元数据条目），与 8558 的长度/难度分布不同。**S1 不能与 S2/S3 拟合同一条曲线**——答辩时主动说清这点，比强行拟合更可信。
5. **curated 层必须单列**：curated 仅 96 条（占 1.1%），若按比例抽 77 条只能抽到 0–1 条精讲，S1′ 就失去了"含精讲的同分布小库"的意义。**抽样时 curated 按固定条数保底（如 S1′ 保 4 条、S2 保 20 条），其余按 `domain × difficulty_tier` 分层**。
6. **各档难度分布必须列表上报**。三档的 L1–L5 占比写进 `scale_sweep.json`，证明抽样没有改变分布。

> **语料难度构成（2026-11-07 入库实测，`data/reports/ingest_report.json` 可核）**：总 **8,558** 条 = 简单 **3,835（44.8%）** / 中等 **3,000（35.1%）** / **困难 1,723（20.1%）**；来源 = curated 96 + CF 5,962 + AtCoder 2,500。与目标配额 45/35/20 基本吻合 —— **因此 §4.3 的拒答集（难 40）在库内有真实可召回样本，`T_none` 不会被标松**。
>
> **五档明细（`03` 统计，仅爬取 8,500 条）**：L1 入门 2,963（34.9%）/ L2 简单 1,103（13.0%）/ L3 中等 1,499（17.6%）/ L4 较难 1,313（15.4%）/ L5 困难 1,622（19.1%）。
>
> **⭐ 三档折叠规则（已裁定，唯一口径）**：**L1+L2 → 简单、L3+L4 → 中等、L5 → 困难**。
>
> ⚠️ **不要把 L4 并进"困难"**（曾有方案折成 L3→中等、L4+L5→困难，得出困难 34.5%，**已作废**）。理由：`rating 1700–1999` 在 CF 约对应 Div2 D，对本科生是"够得着的难"。把它算作"该拒答的困难题"，会让 §4.3 拒答集混入大量**本可回答**的题，`T_none` 直接标歪。按正确折叠，困难 = L5 = **19.1%**，与 DB 三档实测 **20.1%** 基本一致（差 1pp 来自 curated 96 条的分布）。
>
> ⚠️ **全库池 ≠ 入库池**：CF 全库池困难档 57.7%，分层抽样后入库池 19.1%（L5）。**标定阈值必须用入库池分布**，否则阈值与真实检索环境不匹配。
>
> **仍然必须做难度分层评测**，理由不是"库没有困难题"，而是**两类问题的正确行为本就不同**：主指标集测"该答的答对没"，拒答集测"不该答的忍住没"。混在一个分母里，两个都测不准。
>

#### 4.4.2 每档必须记录的指标

| 类别 | 指标 | 为什么必须 |
|---|---|---|
| 阈值证据 | in-scope 组 top1 similarity 的 **p10/p50/p90** | 看 in-scope 分布随 N 如何平移 |
| 阈值证据 | out-of-scope 组 top1 similarity 的 **p10/p50/p90** | 看 out-of-scope 分布右移幅度（hubness 直接体现） |
| 阈值证据 | **in/out 判别 ROC-AUC**（用 top1 sim 区分两组） | **AUC 随 N 下降 = "阈值必须重标定"的量化证据**，一张图说服评委 |
| 阈值证据 | 每档 `calibrate` 输出的 `T_strong / T_weak` | 看阈值漂移幅度 |
| 召回 | Recall@5 / Recall@10 / MRR@10 | 主指标 |
| 判定 | **false_accept_rate**（out-of-scope 被判非 `none` 的比例） | 固定阈值下随 N 上升，是幻觉的直接来源 |
| 判定 | **accept_rate**（in-scope 被判非 `none` 的比例） | 防止为了压 false_accept 把真问题也拒掉 |
| 延迟 | 分环节 P50/P95：`embed / bm25 / ann / fuse / rerank / pack` | 区分"随 N 增长"与"固定成本" |
| 延迟 | 端到端检索 P95（不含 LLM） | 对外承诺数 |

**延迟上的关键洞察（值得单独写进论文）**：只有 `bm25` 与 `ann` 两段随 N 变化；`embed`（每次只编码 1 条 query）、`rerank`（`top_n=24` 固定）、`pack` **都与 N 无关**。因此总延迟随 N 的增长是**亚线性且很快饱和**的——这正好反驳"库大了必崩"的直觉，也是 §3.2 延迟预算成立的前提。

#### 4.4.3 执行顺序与一个必踩的坑

1. 先生成 S3（8558）→ 由 S3 抽样得到 S2、S1′；
2. 用**同一个 test 集（250 条）**跑四档；
3. S1 用 v3 原库单独跑，并注意口径：

> ⚠️ **S1 的口径陷阱**：v3 库仅 77 条，250 条 query 里绝大多数 gold 不在库里。**S1 的 Recall 必须只在"gold ∈ 77 库"的子集上计算**（估计 n ≈ 40–60），否则会被大量必然 miss 拉低到无意义。该子集的 CI 会很宽（n=50 时 ±11pp），**如实标注"小样本，仅作锚点"**，不要拿它和外推曲线强行对齐。

#### 4.4.4 预期趋势（论文假设 + 答辩预判）

| 现象 | 预期 | 若不符说明什么 |
|---|---|---|
| in-scope top1 sim | 随 N 小幅上升（+0.01~0.05） | 大幅上升 → 模型对干扰项不敏感，考虑换 embedding |
| out-of-scope top1 sim | 随 N 明显上升（hubness） | **这就是阈值必须重标定的物理原因** |
| 判别 AUC | 随 N 下降（0.95 → 0.85 量级） | 若不降 → 题库同质化高、难负样本不足，需补 |
| false_accept_rate（固定阈值） | 随 N 上升 | **这条曲线是"阈值不能写死"最有力的证据** |
| Recall@10 | 随 N 下降（干扰项变多） | 下降幅度即"为什么必须 Hybrid+Rerank"的动机定量 |
| BM25 检索 P95 | 近线性微增（O(N)，常数小） | 增长过快 → 换 `bm25s` / 优化倒排 |
| ANN 检索 P95 | 亚线性 | 增长过快 → 降 `ef_search`（用 Recall 换延迟） |
| **编码/重排 P95** | **基本不变** | 若变化 → 说明 `top_n` 没截断住，实现有 bug |

#### 4.4.5 产出与呈现

| 项 | 内容 |
|---|---|
| 数据文件 | `experiments/results/scale_sweep.json`（四档 × 全部指标 × 分环节延迟） |
| 图 | `scale_sweep.png`，三张子图（横轴 **log10(N)**）：①延迟 vs N（分环节堆叠）；②AUC 与 T_strong/T_weak vs N；③Recall@10 与 false_accept_rate vs N |
| 拟合 | 仅作趋势参考：`P95 ≈ a + b·log10(N)`、`T_strong ≈ c + d·log10(N)`、`AUC ≈ e + f·log10(N)`。**明确写"拟合仅用于外推讨论，每档仍以实测重标定为准"** |
| 答辩用法 | 被问"扩到 5 万会怎样"时，给 log 拟合的**区间估计** + "当前已在 8000 档标定，扩到 5 万需重跑本组实验"。**比拍一个数字安全得多** |

#### 4.4.6 这组实验的额外收益

一次实验同时产出三样东西：①**阈值必须按库规模重标定的量化证据**（AUC + false_accept 曲线）；②**延迟可扩展性的结论**（证明重排/编码是固定成本）；③**Hybrid 必要性的旁证**——若 N 增大时纯向量 Recall 掉得比 Hybrid 快，则 BM25 的价值随库规模放大，这比在 77 库上调参得出的结论硬得多。

## 5. 上下文打包

### 5.1 Token 预算分配

以 DeepSeek-chat（上下文充裕，但**输入 token 直接决定成本与首字延迟**）为例，**总输入预算 4096 token**：

| 段 | 预算(tokens) | 占比 | 说明 |
|---|---|---|---|
| system prompt | 600 | ~15% | 角色 + 约束（不给完整代码）+ **引用格式规范** |
| 检索资料（上下文） | 2400 | ~58% | 5 条短条目 ×~480，或 3 条长精讲 + 2 条短条目 |
| 历史对话 | 800 | ~20% | 最近 3 轮；超限滚动摘要，不整段硬塞 |
| 当前问题 | 300 | ~7% | 已知被 `MAX_QUERY_CHARS=160` 约束，留余量 |
| **输入合计** | **≤ 4100** | | 超出则按"历史 → 资料"顺序裁剪 |
| 输出预留 `max_tokens` | 2048 | — | 不计入输入 |

**打包算法**：按最终排名顺序累加资料 token，**塞满 2400 即停**（不是"每次都塞 6 条"）；先保证"每条至少保留标题 + 首段"，再补全文。

#### 5.1.1 前置过滤（四条件，缺一不可）

> ⚠️ **必须四条件**：`is_deleted = 0 AND status = 'published' AND sensitivity IN ('L1','L2') AND visibility != 'restricted'`。
>
> **最容易漏的是 `is_deleted`**——前三条件（published / sensitivity / visibility）看起来已经覆盖了"能不能用"，但**软删的条目 `status` 可能仍是 `published`**。漏掉它会让已删除条目继续被召回，表现是"明明删了还在引用里出现"，而且**不报错、不告警**，只能靠人工发现。

| 过滤位置 | 作用 | 为什么两处都要 |
|---|---|---|
| **召回时**（Chroma `where`） | 把脏数据挡在候选集外 | 若不在这里挡，脏数据会占用 50 条召回名额，重排和截断都在为它白干活 |
| **打包前**（最后一道） | 兜底，防增量同步延迟导致的漏网 | 若只在这里挡，候选池已被污染，最终 top-5 可能只剩 3 条干净的——**看起来像"召回不足"，实际是脏数据挤占** |

> **软删的时效性**：如果删除是"标记 `is_deleted=1`"而不重建索引，那么向量库里那条**仍然存在且可被检索**，只能靠 metadata filter 拦住。因此 `is_deleted` 必须**冗余进 Chroma metadata**（不能只在关系库里），否则过滤条件在向量侧无效。
>
> ⚠️ **当前风险（待确认）**：守库核对发现 `knowledge_items` 表只有 13 列，`entry_type`/`visibility`/`sensitivity`/`is_deleted` 等字段**可能不在源表里**。若这些字段没进 Chroma metadata，上面四条过滤**全部失效**——`where` 条件匹配不到任何键，可能返回空集（什么都不召回）或静默忽略（脏数据全放过）。**跑任何实验前必须先验证一条 `where` 查询能否命中**。

### 5.2 同题去重（打包层二次防线）

**与加工侧 `03-知识加工流水线.md §3.3` 的去重键对齐**（两侧用同一套键，避免各去各的）：

| 场景 | 去重键 | 合并规则 |
|---|---|---|
| 同条目多块同时召回 | `(problem_key, chunk_type)` | 留最高分块；命中 head/tail 时回填父块 |
| curated 与 crawled 关联对 | `problem_key` | **curated 优先**，crawled 降为补充证据 |
| 相邻难度同模板题 | `(normalized_title, difficulty)` | 留 1 条，其余降为"相关推荐" |
| 重爬重复块 | `(chunk_id, content_hash)` | 入库已 upsert 唯一，检索期兜底 |
| 同 `tag` 条目（多样性） | `tag` | **最多 2 条**，防 5 条全是"动态规划"（MMR-lite） |
| 超长条目 | — | 单条 > 480 token 截断到"首段 + 关键结论句" |

**首批事实（据 `03 §3` 实测）：8,558 条中 8,552 条单块；仅 6 条（601–1200 字符，集中在网络流/后缀数组/树链剖分等新增知识点卡）按 `【】` 切 2 块各自入库**（`slice_idx=0/1`），**不建父链、不做回填**。故总 chunk ≈ **8,564**。

> **父子链机制本轮不启用**：6 条远低于"≥100 条多块语料才建父链"的门槛。规则与代码保留，作为二期长题解语料预案。
>
> ⚠️ **但去重键必须现在就落代码**——v3 的"长精讲切 5 片、RRF 里吃 5 份分数、把第 2 名挤掉"缺陷，触发条件是**同题多块**；这 6 条一入库就已经满足条件（同一 `problem_key` 出现 2 块）。虽然只有 6 条、影响面小，但**去重键不加就是错的**，而且二期一放大就会复发（见 §2.3 融合前塌缩）。

| 情况（二期长文本启用后） | 回填策略 |
|---|---|
| 子块命中，父块 ≤ 600 字符且资料预算够 | 回填**整条父块**，同题其他块丢弃 |
| 子块命中，预算不够 | 只回填 **prev/next 各 1 块**（局部上下文） |
| 预算已满 | **不回填**，保留子块原文 |

> **为什么不默认全回填**：资料预算仅 2400 token。ACM 场景下"**5 个不同题目的考点** >> **1 个题目的完整文档**"——学生问"01背包为什么倒序"，要的是"考什么、典型套路"，不是把三段式全文读完。因此**回填优先级必须低于"召回更多不同题"**。

> **去重 ≠ 形态加权**：去重解决**同一道题**的重复（只有约 120 个 `problem_key` 会同时有精讲类与考点提示）；但 top-5 更常见的情况是**5 道不同的考点提示**把唯一精讲挤到第 8 位——那是**跨题**失衡，只能靠 §2.2.1 的 `w_type` 解决。两者互补，都要保留。

### 5.3 引用编号格式

**格式固定、可解析、可回链，且按 `entry_type` 分型**（分型是幻觉控制的关键，见 §9 两维度说明）：

```
[1] 01背包（精讲 · 中等 · 动态规划/背包）
    题解要点：……
[2] 网络流基础（知识点 · 困难 · 图论/网络流）
    知识点：……
[3] CF1932F（考点提示 · 中等 · 动态规划/背包）
    考点：本题考查……典型套路是……
```

| `entry_type` | 引用标记 | 允许的内容边界 |
|---|---|---|
| `solution`（题解卡） | 「精讲」 | 可给完整思路与复杂度 |
| `concept`（知识点卡） | 「知识点」 | 可讲概念与适用场景，**不给具体题目答案** |
| `strategy`（元知识） | 「元知识」 | 可讲学习路径/方法，**不涉及具体题目** |
| `hint`（考点提示，爬取 8,462 条） | 「考点提示」 | **只可描述考查方向与典型套路，不得推断具体复杂度或数据结构选择** |

- **编号 = 最终展示顺序**（不是原始分数顺序），一次响应内稳定；配额插入后编号随之重排。
- 每条带 `平台 / 题号`，便于学生回原题；`[n]` 前端做成可点击锚点（对应 `problem_key`）。
- 正文引用用 `[1][3]` 紧贴结论句，**禁止出现无对应资料的编号**。
- **前端不展示任何相关性分数**——只展示编号、标题、形态标记、难度。

**system prompt 内的引用规范片段（建议原文）**：
> 回答必须以检索资料为依据，凡引用题库条目须用 `[编号]` 标注。标为「考点提示」的条目只可描述考查方向与典型套路，不得据此推断具体复杂度或数据结构选择。若资料不足以回答，不得虚构，须明确说明"题库未收录相关内容"。

### 5.4 资料不足时的降级话术

| 触发 | 话术模板 |
|---|---|
| `none`（未收录） | "题库暂未收录与「{query}」直接相关的题目。以下基于通用算法知识给出思路，请结合具体题目核对题意与数据范围。\n\n（通用分析）……\n\n> 如需更精准的题解，可补充题目来源（平台+题号）或贴出题面关键条件。" |

## 6. 评测协议

### 6.1 qrels 构建（自动生成 query 与相关性标签）

**目标**：约 8558 条库（curated 96 + crawled 8462），人工标注不现实，但**标签必须有依据、可复现、可审计**。

**Step 1 · 查询生成（从条目反向生成）**

| 条目类型 | 生成方式 | 每条生成数 |
|---|---|---|
| **curated 精讲（96 条）** | LLM 从"题解思路 + 常见错误"生成**学生口吻**提问：① 概念型"X 为什么…"；② 错误型"我写成…为什么错/WA/TLE"；③ 追问型短句"那内层为什么倒序" | 2–3 条 |
| **crawled 考点提示（8462 条）** | 模板 + LLM：`{题名} 怎么做` / `{标签} 的 {题名} 思路` / 贴题号问法。⚠️ 因条目只有考点拆解、无题面，生成时**禁止**问"这题的边界数据范围是多少"这类只有题面才能回答的问题 | 1–2 条 |
| 未收录负样本 | 从题库**未覆盖**的知识点构造 30–50 条（如线段树合并、可持久化并查集） | — |

**curated 96 条必须拆三套模板**（结构不同，套同一模板会产出怪 query）：

| 子类型 | 条数 | query 生成侧重 | 预期 `query_type` |
|---|---|---|---|
| 题解 | 66 | 概念型 + 错误型 + 追问型（有"常见错误"字段可用） | `concept` / `error` |
| 元知识 | 11 | "XX 和 YY 有什么区别"类 | `concept` |
| **知识点卡** | **19** | **"XX 是什么/怎么用/适合什么场景"**，**禁止**造"我写错了"类（无错因字段） | **`concept` 为主** |

> 66 + 11 + 19 = 96 ✓
>
> **对配额的影响**：元知识与知识点卡基本产不出 `identifier` 类，所以 `identifier ≥ 50` 的配额**只能靠 crawled 的"代码信号问法 + 标签缩写问法"凑**，不要指望 curated 这 96 条。

> **配额注意**：96 条精讲 ×2.5 ≈ 240 条 query，crawled 只需抽 300–400 条生成 query 即可（不必 8462 条全覆盖），否则评测集被 crawled 淹没、精讲类指标样本不足。

**Step 2 · 相关性分级（graded relevance）**

> ⚠️ **v3 时期"共享 ≥1 个核心 tag 即 rel=1"的规则在 8558 条库上必须废弃。**
> 理由：单个人气 tag（如"动态规划"）在 crawled 里可覆盖数百条，`rel=1` 会瞬间廉价化——每个 query 有上百条 rel=1，IDCG 被撑大、NDCG 失去区分度，且人工复核成本爆炸。

| 等级 | 判定规则（自动） | 数量约束 |
|---|---|---|
| **2（gold）** | 生成 query 的源条目（`problem_id` 精确匹配；同题多切片合并计一条） | 1 条 |
| **1（可接受）** | 同时满足：① **tag Jaccard ≥ 0.5**（标签集合高度重叠，而非共享 1 个）；② 难度差 ≤ 1 档；③ 与 gold 非同一 `problem_id` | **每 query ≤ 8 条**，按 Jaccard 降序取 |
| **0（不相关）** | 其余 | — |
| **hard negative** | BM25/向量 top-20 中 `rel=0` 且 tag Jaccard > 0 的条目 | 每 query 5–10 条 |

**三条补充规则**：
1. **同题多切片只算一条**：一个 `problem_id` 被切成 3 片，不能给 3 条 rel=2/1，否则 NDCG 被切片数污染（与 §2.3 融合前塌缩是同一个道理）。
2. **curated 优先**：若同 tag 下同时存在 curated 与 crawled 的 rel=1 候选，且名额不足 8 条，**优先保留 curated**（信息量更足）。这条要写进标注工具，不能靠人工临场判断。
3. **rel=1 必须扩大人工抽检**：自动判定的 rel=1 直接决定 NDCG 是否可信，抽检比例从 10–15% 提高到 **20%**，重点看 Jaccard ≥0.5 的边界样本。

**Step 3 · 质量抽检**：随机抽 10–15%（rel=1 部分 20%）人工复核，报告**标注一致率**（目标 ≥ 90%）与 Cohen's κ（目标 ≥ 0.7，三级标注 κ=0.6 偏低）；不一致样本修正后回灌。这条在论文里是"标注可信度"的证明材料。

**Step 4 · 切分**：dev 60% / test 40%，**按题目切分防泄漏**（同一题的生成 query 不得跨集）。

### 6.1.1 查询分层（子集结论的前提）

要出"某类查询提升 X"的子集结论，必须先有**互斥、可判定**的分层规则（否则标注者会各判各的）：

| 层 | 判定规则（优先级从上到下，命中即定层） | 典型样例 |
|---|---|---|
| **T4 题号型** | 含平台+题号（`CF\d{4}`、`ABC\d{3}`、`AtCoder ... _[a-z]`） | "CF1932F 怎么做" |
| **T3 标识符型** | 含算法术语缩写（LIS/KMP/DP/BFS）、函数/变量名（`lower_bound`、`dp[j]`）、题名片段 | "LIS 的 n log n 写法" |
| **T2 报错型** | 含 TLE/WA/RE/MLE/死循环/超时/段错误/答案错误 | "这题 TLE 了为什么" |
| **T1 概念型** | 其余（问原理/区别/为什么，无上述信号） | "01 背包为什么倒序" |

**样本量与置信区间**（比例估计 `p≈0.8`，95% CI 半宽 `≈1.96·√(p(1-p)/n)`）：

| test 集规模 | 95% CI 半宽 | 能否支撑"提升 10pp"的结论 |
|---|---|---|
| 60 | ±10.1 pp | ❌ 与噪声同量级 |
| 100 | ±7.8 pp | ⚠️ 勉强 |
| 150 | ±6.4 pp | ✅ 可 |
| 200 | ±5.5 pp | ✅ 稳 |

**分层样本量**：若 T3 子集只有 30 条，其 CI 半宽约 ±14 pp——**"T3 +25pp"这类结论必须 T3 ≥ 50 条**才站得住。因此建议：**总量 250 条（dev 100 / test 150），四层在 test 内各 ≥ 30 条，重点层（T3）≥ 50 条**。150 条总量只够报**整体指标**，不够报子集。

### 6.1.2 基线的两套口径（分母必须唯一且写明）

v3 的 `retrieval_eval.py` 调的是 `retrieve(..., n_results=10, rerank=False)`，它会走 `_select_relevant` 三闸——**`best_distance > 0.68` 时直接返回空列表**，该 query 的 Hit@5 记 0。这意味着它测的是"最终递交给 LLM 的列表"，**不是"纯召回能力"**。两套口径混用会让"提升 X%"的分母出错。

| 基线 | 口径 | 用途 | 论文位置 |
|---|---|---|---|
| **B1 纯召回** | 跳过三闸，直接取向量 top-10 | 衡量**检索能力**，消融对比用这个 | §5 消融表 |
| **B2 线上行为** | 完整 v3 链路（三闸生效） | 衡量**端到端拒答与幻觉** | §5 拒答/幻觉小节 |

**冻结要求**：B1、B2 必须在固定 test 集上跑出并写入 `experiments/results/baseline_v3.json`，含 `n / Recall@5 / Recall@10 / MRR@10 / NDCG@10 / P@5 / 空结果率`。三闸导致的"空结果率"本身就是一个有意义的指标（v3 在 77 库上的拒答行为），值得单独报告。

**⚠️ 空结果率必须拆成两类再用（否则会变成丢分项）**：

| 类型 | 定义 | 论证价值 | 该放哪 |
|---|---|---|---|
| **真拒答** | 77 条库里**确实没有**能回答的条目 | ✅ **扩库动机**（立论） | 问题定义章 |
| **假拒答** | 库里有相关条目，但被三闸（`best_distance > 0.68`）**误拒** | ✅ **v4 分位数重标的必要性**（改进论据） | 方法/动机章 |

- **拆分方法**：从 B2 的空结果 query 中抽 50 条，人工判断"77 条库里是否真的存在能回答的条目"（只判有无，不判好坏）。约 1 小时。
- **禁止把两类合并成一个"空结果率 40%"**——那样既不能证明扩库必要，也不能证明阈值有问题，只剩负面印象。
- **空结果率必须按难度分层报**：77 条库基本是简单/中等题，困难题查询必然空。分层表本身就是扩库动机最硬的证据。

### 6.1.3 `query_type` 打标（分桶结论的前提）

> ⚠️ **必须先纠正一个方法论错误：生成方式 ≠ `query_type`。**
> "标题问法 / 标签问法 / 代码信号问法"是**制造 query 的手段**；`query_type` 是 **query 的语言学形态**。一条"标签问法"生成的 query 可能落 `concept`（"背包问题怎么入门"），也可能落 `identifier`（"LIS 怎么写"）。若按生成方式直接映射类型，分桶结论必然有偏。

| 生成方式 | 典型产出 | 可能落入的 `query_type` |
|---|---|---|
| 标题问法 | "{题名} 怎么做" | `concept`（无缩写）或 `problem_id`（题名带题号） |
| 标签问法 | "{标签} 怎么写/怎么选" | `concept` 或 `identifier`（标签是缩写如 LIS/KMP/DP 时） |
| 代码信号问法 | "`dp[j]` 为什么越界"、"`lower_bound` 返回什么" | **`identifier`（绝大多数）** |
| 真实会话日志 | 学生原话 | 按形态判定，不预设 |

**判标流程**：先生成 query → **再**按 §6.1.1 的 T1–T4 规则判定 → 写入 `query_type` 字段。**不得按生成方式直接赋值。**

**可执行判定规格（实现者照此写，不要用 LLM 判）**——按顺序匹配，**命中即定层并 break**：

| 层 | 判定正则 / 规则 |
|---|---|
| **T4 题号型** | `(?i)\b(CF\|Codeforces)\s*\d{2,5}[A-Z]?\b` 或 `(?i)\bABC\s*\d{2,4}[_ ]?[A-Z]\b` 或 `(?i)\b(AtCoder\|ARC\|AGC)\s*\d{2,4}` |
| **T3 标识符型** | `(?i)\b(LIS\|LCS\|KMP\|BFS\|DFS\|DP\|MST\|FFT\|NTT\|SG\|ACAM\|SAM)\b`；或含数组/函数下标 `\b[a-z_][a-z0-9_]{1,20}\s*\[`；或含下划线标识符 `\b[a-z]+_[a-z]+\b` |
| **T2 报错型** | `(?i)(TLE\|WA\|RE\|MLE\|OLE\|CE\|超时\|死循环\|段错误\|答案错误\|运行错误\|内存超限)` |
| **T1 概念型** | 以上都不匹配（兜底） |

**三条实现纪律**：

1. **禁止用 LLM 判 `query_type`**——不可复现，同一 query 两次跑出两个类型，答辩无法解释。规则脚本可复现、可审计。
2. **判定结果必须落盘可查**：`qrels_source.jsonl` 每条带 `query_type` + `matched_rule`（命中的是哪条正则），答辩可直接展示匹配证据。
3. **人工复核 10–15%，重点看 T3**——正则最易误伤（如 "DP 值" 被误判为动态规划）。

**分桶配额（决定"identifier +25pp"这条结论能否成立）**：

| `query_type` | test 集目标 | 说明 |
|---|---|---|
| `concept` | ≥ 30 | |
| `error` | ≥ 30 | |
| **`identifier`** | **≥ 50** | 创新点分桶结论的唯一支撑，低于 50 条 CI 放宽到 ±14pp，pp 结论不可写 |
| `problem_id` | ≥ 30 | |

**配额必须在生成阶段反向控制，不能事后统计。** 自动池 75 条里主动多造 `identifier`（用"代码信号问法"+"标签缩写问法"各 20 条）；真实日志 75 条按自然分布，缺口从自动池补足。**等生成完再统计，缺的补不回来。**

**两条预期管理（务必写进论文，否则答辩对不上）**：
1. **`identifier +25pp` 只能在 8000 条库上做出来**。77 条小语料里每个 tag 仅 2–3 条，BM25 与向量都能召回，差不出 25pp。
2. 纯向量基线在 `identifier` 类上**本来就差**（缩写/OOV 是 embedding 的固有短板），所以 +25pp 在 8000 库上是可信的；但如果实测只有 +8pp，如实报——**负结果比拔高数字安全**。

### 6.1.4 qrels 双格式转换层（同机双跑的前提）

v3 与 v4 的输入格式不同，**必须由单一真源导出两份，不能各写各的**：

| 脚本 | 输入格式 |
|---|---|
| v3 `scripts/retrieval_eval.py` | `{"query": str, "expect": ["两数之和", ...]}`（**title 子串匹配**） |
| v4 `eval` | `{"qid", "query", "query_type", "qrels": {"cf-1932-f": 2, ...}}`（**problem_id → 0/1/2**） |

```
qrels_source.jsonl        ← 唯一真源（problem_id + 0/1/2 + query_type）
   ├─ export --format v4     → qrels_v4.jsonl
   └─ export --format legacy → qrels_legacy.jsonl   ← v3 直接可读
```

**legacy 导出规则**：`expect` = 该 query 下 `rel == 2` 的条目的**原始 `title`**。⚠️ 不要用归一化后的标题（`01背包` 不能被 norm 成 `01 knapsack`），否则 v3 的子串匹配会全部 miss。

**判定逻辑必须对齐的三处**（不同则数字不可比）：

| 项 | 统一约定 |
|---|---|
| 候选池 | 均为 **top-10**（v3 已 `n_results=10`；v4 用 `--top-k 10`） |
| 命中判定 | Hit@K：top-K 内存在 `rel==2`；MRR@10：首个 `rel≥1` 的倒数排名；NDCG@10：按 0/1/2 分级（见 §6.2.1） |
| 三闸 | **双跑对比必须两边都关闭**：v3 加 `--no-gate`，v4 加 `--gate off`。只有 B2（线上行为）对照才开启 |

> ⚠️ **`--gate off` 必须同时置空 `max_distance` / `weak_distance`，否则等于"半关闸"**——只关判定逻辑但保留距离参数，会得到既非 B1 也非 B2 的第三种口径，数字无法与任何基线对照。
>
> ⚠️ **严禁"v3 开闸 vs v4 关闸"混比**：v3 的 `RAG_MAX_DISTANCE=0.55/0.68` 是 **L2 距离**，v4 的 `strong_threshold/weak_threshold` 是 **cosine 相似度**，两者语义与量纲都不同，混比得出的"提升"没有任何意义。**开闸对开闸、关闸对关闸，两组分开报。**

**v3 侧最小改动（不动业务逻辑，约 15 行）**：在 `retrieval_eval.py` 加 `--no-gate` 分支，该模式下直接 `collection.query(query_texts=[q], n_results=10)` 取原始 top-10，**跳过 `_select_relevant`**；`rag.py` 一行不改。这样 v3 的 B1 与 v4 的 G2（Vector only）才是同一口径。

**77 条小语料双跑的两条技术提醒**：

1. **BM25 的 IDF 在 N=77 时不稳定**（`n(t)` 小、方差大，罕见词 IDF 可能异常高）。所以 **77 条上的 Hybrid 数字只用于"结构等价性验证"，不用于论证 BM25 的价值**；BM25 价值必须在 8000 档（§4.4 S3）上论证。
2. **77 条上 Hybrid 增益必然很小**（G3≈G2 是正常的，不是失败）。若双跑时看到 G3 明显优于 G2 反而要怀疑——可能是 qrels 泄漏或 title 匹配过宽。

### 6.1.5 双跑一致性校验（`eval --verify`）

比"看指标是否接近"更早暴露实现错位的是**两级一致性检查**，按顺序做：

| 级别 | 检查 | 通过标准 | 不通过说明 |
|---|---|---|---|
| **L1 向量级**（最先查） | 同一 query、同一批文档，v4 与 v3 的 **top-1 余弦相似度数值** | 差 **< 0.01** | embedding 模型版本 / 归一化 / 距离度量不一致 —— **不用查排序，直接查向量** |
| **L2 排序级** | 同一 query，v4 `G2` 与 v3 `--no-gate` 的 **top-3 集合 Jaccard** | **≥ 0.8** | 文本表示或分词口径不同（见下方 ⚠️） |
| **L3 指标级** | Hit@1/3/5、MRR@10、NDCG@10 差异 | **≤ 1pp** | 判定逻辑（补 0 / IDCG / rel 阈值）不一致 |

> ⚠️ **L2 的 0.8 阈值有一个前提：两边 embedding 文本必须同构。**
> 已核实 v3：`rag.py:351` 是 `documents=[item["content"]]` —— **只 embed `content`，`title` 仅存在于 metadata**。
> 因此 v4 必须提供 `embed_text_mode` 配置：
> | 模式 | 用途 |
> |---|---|
> | `content_only`（**默认**，与 v3 严格对齐） | 基线双跑、一致性校验、G1–G4 消融 |
> | `title_plus_content` | **单独实验 E11**，标题含算法术语，预计有正收益，但**会改变所有基线数字** |
>
> **排期纪律**：先用 `content_only` 跑完全套 G1–G4 + L1/L2/L3 校验并**冻结基线**，再单独做 E11。反过来会陷入"基线数字一直在变"。

### 6.2 指标定义

| 指标 | 定义 | 用途 |
|---|---|---|
| **Hit@1 / @3 / @5** | top-K 内**至少一条** `rel==2` 的 query 占比（v3 历史口径，与旧数据可比） | **主 KPI**（正式口径第一项） |
| **Recall@5 / @10** | top-K 内命中的 gold 数 ÷ 该 query 的 gold 总数；**单 gold 时与 Hit@K 等价**，多 gold 时更严 | 召回能力（子集分析用） |
| **MRR@10** | `mean(1/rank_first_relevant)`，`rel≥1` 视为命中，rank>10 记 0 | 排序质量（头部精度） |
| **NDCG@10** | `DCG@10 / IDCG@10`，`gain = 2^rel − 1`，`discount = log2(i+1)`（Järvelin & Kekäläinen, 2002）；**实现约定见 §6.2.1** | 分级相关性排序质量（最贴近实际体验） |
| **Precision@5** | 前 5 条中 `rel≥1` 占比 | 上下文洁净度（直接对应幻觉率） |
| **拒答正确率** | 未收录查询被正确判 `none` 的比例 | 拒答闸门有效性 |
| **P95 / P50 延迟** | 检索全链路（不含 LLM）毫秒 | 工程可用性 |
| **幻觉率** | 人工抽检回答中出现"资料未支持的具体断言"的比例 | 端到端效果 |

> **正式口径五项**（与毕设定位文档 §3.5 对齐）：`Hit@1 / Hit@3 / Hit@5 / MRR@10 / NDCG@10 / P95 延迟`。其余指标为内部诊断用，论文正文可放附录。

### 6.2.1 NDCG@10 计算约定（v3 与 v4 实现必须逐条一致）

NDCG 是最容易被两个人写出两个数的地方，下面 5 条约定**任一不一致都会导致 v3/v4 不可比**：

```python
def dcg(gains):                     # gains: 按检索排名顺序的 rel 值
    return sum((2**r - 1) / math.log2(i + 2) for i, r in enumerate(gains))

def ndcg_at_10(ranked_rels, all_labeled_rels, k=10):
    got   = (list(ranked_rels) + [0] * k)[:k]          # ① 不足补 0
    ideal = sorted(all_labeled_rels, reverse=True)      # ② 用全部标注集
    idcg  = dcg((ideal + [0] * k)[:k])
    return dcg(got) / idcg if idcg > 0 else 0.0
```

| # | 约定 | 说明 |
|---|---|---|
| ① | **结果不足 10 条补 0，而不是截断后重算 IDCG** | 最易分歧点。补 0 保证分母稳定 |
| ② | **IDCG 的候选来自"该 query 的全部标注条目"**，不是检索结果里出现的 | 多数 query 只有 1 条 gold → IDCG = 3 |
| ③ | `gain = 2^rel − 1` → rel 0/1/2 得 **0 / 1 / 3**（指数增益） | 与 `gain = rel`（线性 1:2）结果**不同**。推荐指数，但**必须两边一致并在论文写明用了哪种** |
| ④ | `discount = log2(i+2)`（i 从 0 起）≡ `log2(rank+1)`（rank 从 1 起） | 统一用 rank 从 1 起的写法更不易错 |
| ⑤ | **主集**空结果（三闸拒答）→ **NDCG = 0 且计入平均** | 防止空列表被静默剔除、掩盖系统失败 |
| ⑥ | **无正例 query（拒答集）→ 不计入任何检索指标的平均**，只统计"拒答正确率" | 拒答集本来就"没有正确答案"，把它算进 NDCG/MRR 等于**用不该答的题惩罚系统**，会把主集指标拉低、掩盖真实性能 |

> ⚠️ **⑤ 与 ⑥ 必须分开**，这是最容易被写成一处的地方：
> - **主集 100 条**：都有 gold。系统若返回空 → 记 0 并计入平均（这是失败）。
> - **拒答集 50 条**：**故意没有** gold（困难/超纲）。系统若返回空 → **正确行为**，不能记 0，也不进平均。
>
> 判断依据是 **query 属于哪个子集**（`subset ∈ {main, refusal}`），**不是"结果是否为空"**。用"结果是否为空"判断会把两个子集混在一起。

**为什么必须有 NDCG（回应"qrels 是 0/1/2 三档"）**：Hit@K 只认 `rel==2`，会把"命中 `rel=1` 的合理替代"记为完全失败。例：query"01背包遍历方向"，排第 1 是 `完全背包`（rel=1）、排第 2 是 `01背包`（rel=2）——Hit@1 = 0 但 NDCG@10 ≈ 0.79。**G3/G4 之间的差异主要就体现在这种"第 1 名是 rel=1"的样本上**，所以 NDCG 是消融表的关键列，不能省。

### 6.3 消融矩阵（4 组必做 + 2 组扩展）

| 组 | 配置 | Hit@1 | Hit@5 | MRR@10 | NDCG@10 | P95 延迟 |
|---|---|---|---|---|---|---|
| G1 | **BM25 only** | 待测 | 待测 | 待测 | 待测 | ~20 ms |
| G2 | **Vector only**（v3 行为） | 待测 | 待测 | 待测 | 待测 | ~25 ms |
| G3 | **Hybrid（加权 RRF）** | 待测 | 待测 | 待测 | 待测 | ~40 ms |
| G4 | **Hybrid + Rerank**（v4 完整） | 待测 | 待测 | 待测 | 待测 | ~450 ms |
| G5（扩展） | G4 + 查询改写 | — | — | — | — | +50 ms |
| G6（扩展） | G4 + 元数据软加权 | — | — | — | — | +5 ms |

**表内纪律**：① 全部为 `--no-gate`（B1 口径）下的数字；② G2 必须与 v3 的 `--no-gate` 双跑结果一致（差 >1pp 说明实现口径没对齐，先修脚本再往下做）；③ 延迟列为 CPU 单机 P95，标注机器型号。

**预期趋势（用于论文假设）**：G3 相对 G2 的 **Recall@10 提升最大**（补上精确匹配短板，约 +4~8 点）；G4 相对 G3 的 **MRR/NDCG 提升最大**（头部排序，约 +5~10 点），代价是延迟 ×10。若 G3≈G2 或 G4≈G3，说明该改动在本语料上无效，**如实报告**——负结果同样是工作量。

### 6.4 显著性检验建议

| 目的 | 方法 | 说明 |
|---|---|---|
| 指标置信区间 | **Paired Bootstrap**，10,000 次重采样，95% CI | 报告 `Recall@10 = 0.82 [0.79, 0.85]` 而非单个点 |
| 两系统差异显著性 | **Wilcoxon signed-rank test**（逐 query 配对，非参数） | 不假设正态；`p < 0.05` 判显著 |
| 效应量 | **Cohen's d** 或相对提升 % | 说明"提升了多少"而不只是"显著" |
| 多重比较 | Holm-Bonferroni 校正 | 消融 6 组两两比较时防假阳性 |

**纪律**：dev 上调参，test 只跑**一次**；禁止在 test 上反复调阈值（数据窥探）。

## 7. 调参实验表（论文第 5 章素材）

| # | 实验名 | 自变量 | 因变量 | 预期结论 |
|---|---|---|---|---|
| **E1** | BM25 分词方案 | jieba / 字 bigram / 混合 | Recall@10、Precision@5（中文子集 vs 英文子集） | 混合最优；jieba 在中文子集领先 bigram 3–6 点，bigram 在题号子集不劣 |
| **E2** | BM25 参数网格 | `k1∈{1.2,1.5,1.8}` × `b∈{0.5,0.6,0.75}` | Recall@10、MRR@10 | `k1=1.5,b=0.75` 落在平坦最优区；若加工侧条目补到 ~180 字（长度分布趋单峰），`b=0.6` 可能更优 → **需实测** |
| **E3** | RRF k 与权重 | `k∈{10,20,60}` × `w_bm25∈{0.5,0.8,1.0,1.2}` | MRR@10、NDCG@10 | 加权 RRF 优于等权；`k=60,w=0.8` 为稳健最优 |
| **E4** | 召回池规模 | `recall_k∈{30,50,100}`，候选池 30/60/100 | Recall@10 vs P95 延迟 | 50 后边际收益递减，60 是性价比拐点 |
| **E5** | 重排 top_n | `top_n∈{12,24,36,50}` | NDCG@10、P95 延迟 | 24（as-built）附近为最优折中；50 延迟超预算、指标增益 <1 点 |
| **E6** | 阈值标定方式 | 固定 0.55/0.68 vs 分位数标定 | Precision@5、拒答正确率、幻觉率 | 分位数标定在 8000 库上显著更优（防 hubness 误判） |
| **E7** | 四组消融 | G1/G2/G3/G4 | 全套指标 + 延迟 | 见 §6.3 预期趋势；Hybrid 提召回、Rerank 提排序 |
| **E8** | 查询改写增益 | 改写 on/off（仅追问子集） | MRR@10（追问子集） | 追问子集 MRR 提升显著（+8~15 点），直问子集几乎无变化 → 验证"仅追问触发"策略 |
| **E9** | **库规模扫描**（§4.4） | N ∈ {S1′=77, S2=2000, S3=8558} | Recall@10、false_accept_rate、判别 AUC、分环节 P95 | AUC 与 false_accept 随 N 恶化 → 阈值必须重标定；编码/重排延迟不随 N 变 → 延迟可扩展 |
| **E10** | **形态加权**（§2.2.1） | `w_type(curated) ∈ {1.0, 1.1, 1.15, 1.25}` + 配额开关 | NDCG@10、top-5 中 curated 占比、人工可读性打分 | **1:88 比例悬殊，权重效应被放大**，1.15 可能是拐点；`≥1.25` 时 NDCG 可能反降（低分精讲挤进 top-5） |
| **E11** | **Embedding 文本表示**（§6.1.5） | `embed_text_mode ∈ {content_only, title_plus_content}` | Recall@10、MRR@10、NDCG@10 | `title_plus_content` 预计正收益（标题含算法术语）；**必须在基线冻结后单独做**，否则基线数字无法固定 |

**实验记录规范（写进 `experiments/results/`）**：每组必须留 `config snapshot + 指标 JSON + P95 延迟 + 失败样本 top-10`，失败样本是论文"错误分析"小节的一手材料。

| 来源 | 规则 | 说明 |

**难度字段（实际存储只有两列，五档由 `rating` 派生——不要写成三个独立列）**：

| 字段 | 存储？ | 取值 | 用途 |
|---|---|---|---|
| `difficulty` | ✅ 实际存储 | `简单/中等/困难/未知`（三档） | UI 展示、**硬过滤**（§1.5） |
| `rating` | ✅ 实际存储 | 原始数值（CF rating / AtCoder difficulty，可为负或空） | **派生根**：五档与 L1–L5 都由它算 |
| `difficulty_tier` | ❌ **派生** | `L1–L5` | 软加权距离衰减（§1.5）、分层抽样（§4.4） |

**派生规则（`crawler/taxonomy.py::cf_tier()` 是唯一事实来源，不要另拍切点）**：`rating < 1200` → L1 入门；`< 1400` → L2 简单；`< 1700` → L3 中等；`< 2000` → L4 **较难**；`≥ 2000` → L5 困难。**三档折叠：L1+L2 → 简单、L3+L4 → 中等、L5 → 困难**；`rating` 缺省 → `difficulty=未知`、`tier=null`。

> ⚠️ **L4 必须折进"中等"，不能折进"困难"**（详见 §4.4 的裁定说明）。折错会把困难档从 19.1% 虚增到 34.5%，并让拒答集混入大量本可回答的题。

> ⚠️ **两处易错**：① L4 的中文名是 **`较难`**（不是"提高"），别名可写成 `提高 ≡ 较难` 但字段值用 `较难`；② **不要按 1800/2100 切**（这是早期版本），以 `taxonomy.py` 的 1700/2000 为准。
>
> ⚠️ **同名陷阱**：五档里的"简单/中等/困难"与三档 `difficulty` 同名，**靠 `tier` 数值（L1–L5）而非中文名区分**，消费侧代码严禁按中文名分支。

**`et_hints`（可选）**：`metadata.et_hints` 存 ≤2 个错因码（ET01–ET15）。**只能做过滤/加权，不能参与语义匹配**（它是元数据不是正文）。可能的用法：用户问"为什么 TLE"时按 `et_hints=ET07` 提升相关条目——属可选优化，不进默认链路。

**四个正交维度（as-built：`w_type` 挂 `source=="curated"`，2026-11-08 裁定）**：

| 字段 | 实际值域 | 决定什么 | 检索侧消费 |
|---|---|---|---|
| `source` | **`curated` / `cf` / `atcoder` / `manual`**（as-built，语料来源） | 引用展示 + **`w_type` 挂载点**；权利主体由 `url`/`platform` 派生（`codeforces.com` / `atcoder.jp` 域名即权利主体） | ✅ 引用展示 + 加权 |
| `corpus_type` | `curated` / `crawled` | 语义冗余备份（当前不进打分公式） | ⚠️ 当前未被检索侧读取 |
| **`entry_type`** | **`solution` / `concept` / `strategy` / `hint`** | 引用分型（4 型）；**二期细分加权用**，当前不进打分 | ✅ 引用分型 |
| `content_origin` | `self_written` / `metadata` | 合规/守库（防抄袭、溯源） | ❌ |

**引用分型映射**：`solution`→「精讲」、`concept`→「知识点」、`strategy`→「元知识」、`hint`→「考点提示」。
