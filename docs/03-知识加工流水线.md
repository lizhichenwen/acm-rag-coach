# 03 · 知识加工流水线（Extraction & Structuring Pipeline）

> **文档定位**：本文是「知识库建设专家团」交付链的第 3 环。上承 **02《知识资产盘点与分类分级》**（有哪些源、词表与分级）与 **01《毕设定位与建设路线》**（规模目标），下接 **04《检索与 RAG 调优方案》**（切片怎么被召回）与 **05《安全合规方案》**（哪些内容不能落库）。
> **读者**：实现这套流水线的开发同学。本文所有规则均为**可直接编码**的判定式，不含"视情况而定"。
> **实测口径**：文中所有数量、分布、脏数据比例均来自 2026-11-07 对三个真实源的抓取统计（Codeforces `problemset.problems`、AtCoder Problems `problems.json` + `problem-models.json`、本仓库 `acm_knowledge.txt`），不是估算值。快照文件与统计脚本见 §10。

## 0. 流水线总览

### 0.1 为什么需要"加工"而不是"直接入库"

| 源 | 有什么 | 缺什么 | 不加工直接入库的后果 |
|---|---|---|---|
| curated 精讲 77 条 | 完整中文描述 + 题解思路 + 常见错误 | 没有来源 URL、没有难度量值、没有结构化标签词表 | 可检索但**无法按难度/来源过滤**，无法与爬取题关联 |
| Codeforces 11503 条 | contestId / index / name / rating / tags / solvedCount | **无题面、无题解**、tags 为英文计算机术语 | 英文术语标签与中文精讲库**语义不通**（用户问"哈希表"召不回 `hashing`），rating 800-3500 与"简单/中等/困难"**无映射** |
| AtCoder 9900 条 | id / contest_id / problem_index / name / difficulty | **无 tags（API 根本不提供）**、4723 条无 difficulty | 无标签=**零可检索面**，只能靠标题字符串匹配 |

> 结论：加工的核心产出不是"把英文翻成中文"，而是**把异构元数据投影到同一套中文考点空间 + 同一套难度刻度**，并明确标注哪些结论来自官方数据、哪些是推定。

### 0.2 六个阶段

```
 S0 采集归档        S1 解析            S2 归一             S3 合成            S4 切片           S5 门禁        S6 入库
┌──────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────┐   ┌─────────┐   ┌─────────┐
│ 带时间戳   │   │ curated 行式  │   │ problem_id   │   │ 中文正文      │   │ 600 字符  │   │G1–G10   │   │ upsert  │
│ 原始快照   │──▶│ 状态机       │──▶│ 难度归一      │──▶│ 三段式模板    │──▶│ 阈值判定  │──▶│10 条硬  │──▶│ 幂等键  │
│ raw/*.json│   │ CF/AC 字段映射 │   │ 标签词表映射  │   │ ET 线索挂载   │   │ 重叠/父子 │   │ 校验    │   │ + 断点  │
└──────────┘   └──────────────┘   └──────────────┘   └──────────────┘   └──────────┘   └─────────┘   └─────────┘
  幂等锚点          拒绝≤2%            词表唯一          不编造边界         去重键就绪      三分流        可续跑
```

| 阶段 | 输入 | 输出（中间态表） | 失败动作 | 本文对应章节 |
|---|---|---|---|---|
| S0 采集归档 | 三个 API / 文本文件 | `raw_snapshot`（含 snapshot_date、sha256） | 整批中止 | §7.1 |
| S1 解析 | 快照 | `raw_item`（扁平字段 + source_locator） | reject / manual | §1 |
| S2 归一 | `raw_item` | `norm_item`（problem_id、difficulty_tier、tags_norm） | degrade | §4 §5 |
| S3 合成 | `norm_item` | `doc_item`（8 字段统一 schema） | reject（正文超界） | §2 |
| S4 切片 | `doc_item` | `chunk_item`（chunk_id、parent_doc_id） | — | §3 |
| S5 门禁 | `chunk_item` | `gated_item` + `gate_report` | reject/degrade/manual | §6 |
| S6 入库 | `gated_item` | 向量库 + 元数据库 | retry / 进死信队列 | §7 |

### 0.3 三条全局不变量（贯穿全文，门禁强制校验）

| 编号 | 不变量 | 含义 | 门禁对应 |
|---|---|---|---|
| **INV-1 可溯源** | 每条 `doc_item` / `chunk_item` 必须能定位回原始快照的精确位置 | `metadata.source_snapshot` + `source_locator`（CF/AC 为 JSON 数组下标，curated 为行号区间）必填 | G7 |
| **INV-2 不编造** | 爬取条目**不得出现题面原文、题解步骤、复杂度结论、是否 AC 的断言** | 只能用官方元数据 + 本项目既有知识体系做概率性提示 | G3 + §2.6 |
| **INV-3 幂等** | 同一 `problem_id` 重跑任意次数，库内文档数与内容哈希不变 | upsert 键 = `problem_id`；块级 = `chunk_id` + `content_hash` | G8 (§7.2) |

#### 0.4.2 漏斗：采集子漏斗 + 入库主漏斗（**两级，不可混算**）

**① 采集子漏斗（仅 CF，验证"清洗/去重"可独立计数）**

```
fetched 11,503
  − parse_failed 0    → cleaned   11,503
  − dup             0 → deduped   11,503
  − 未入样       5,503 → sampled    6,000      ← §0.4.5 分层抽样（产品决策，非缺陷）
```

**② 入库主漏斗（全平台，这是对外唯一口径）**

```
爬取配额 sampled   8,500   （CF 6,000 + AT 2,500）
  − skipped           38   （重复/门禁 reject）
  → inserted       8,462
  + curated           96
  → 库内 total     8,558     pass_rate 0.996
```

| 计数点 | 值 | 定义 |
|---|---|---|
`sampled` | 8,500 | 分层抽样后的待入库配额（计划值） |
`inserted` | 8,462 | 成功 upsert 且 `status=published` |
`skipped` | 38 | 重复命中（`content_hash` 相同）或被门禁 reject，二者分开记 |
`curated` | 96 | 文件导入，不经爬取漏斗 |
`total` | 8,558 | = inserted + curated |

> ⚠️ **上一版错误（已修）**：我曾把 `ingested = 5,973` 当作总入库数——那只是 **CF 单平台**的数，AtCoder 的 2,500 完全没进漏斗，导致 01 写 8,462、03 写 5,973 会当场对不上。**对外只引用主漏斗的 8,462 / 8,558**。
>
> **`skipped` 内部必须再拆**：`dup`（`content_hash` 相同，幂等跳过）与 `rejected`（门禁不通过）语义不同——前者是"数据没问题、只是重复"，后者是"数据有问题"。混在一起会让 `pass_rate` 失去意义。

#### 0.4.3 三个阈值的可实现校准（给 01）

| 01 承诺的指标 | 本文实测/可实现值 | 建议写法 |
|---|---|---|
| 重复率 **≤3%** | 键级重复率 **0.0%**；但语义近重复 5–10%（8500 条共用同一三段式模板） | 拆两条：**键级重复率 = 0（硬指标）；语义近重复率 ≤8%（模板同质化，已用 `content_hash` + 标题归一控制）** |
| 必填字段完整率 **100%** | ✅ 可实现，G1 + G9 强制，不入库即 reject | 保留 100%，注明"**由门禁强制，非抽样统计**" |
| 难度覆盖率 **≥90%** | **首批 100%**（分层抽样要求 `rating`/`difficulty` 非空）；全量池仅 74.7%（CF 97.3%、**AC 49.4%**） | 必须带范围：**"首批入库 100%；全量池 CF 97.3% / AC 49.4%，缺失标 `未知`"** |

| 项 | 做法 |

| 源 | 规则 | 参数 |
|---|---|---|

> **对 04 的直接回答**（这是 04 明确要的两个数）：
> 1. **601–1200 档条目数 ≈ 6 条**（只是 43 张知识点卡里超长的那 6 张）。按 04 的判断"<100 条就整条入库、不建父链"，**结论：不建父链**——这 6 条按 `【】` 切 2 块后各自独立入库（`slice_idx=0/1`），不挂 `prev/next`，也不做父块回填。

> 另给 04 一条**抽样可用性**提醒：CF 难档只抽了 1200/4902（24.5%），所以"库里困难题"是**抽样后的子集**，不是全库；做 §4.4 库规模实验时若对比 S1′/S2/S3，抽样比例必须一致，否则难度分布不可比。

#### 0.4.7 为什么 120 条精讲是"必须"而不是"锦上添花"（量化依据）

数盘实测给了这条硬证据：CF 全库中 `schedules` 只有 **16 题**、`chinese remainder theorem` 只有 **26 题**——**低于任何"每知识点 ≥30 条"的覆盖底线，且爬虫永远补不齐**（全库就这么多）。

| tag | 全库条数 | 能否靠爬取达到 ≥30 条/知识点 |
|---|---|---|
| `schedules`（区间调度） | **16** | ❌ 不可能 |
| `chinese remainder theorem`（中国剩余定理） | **26** | ❌ 不可能 |
| 交互题 / 构造（策略类） | 少量且分散 | ❌ 不可能 |

> 结论：**这 120 条精讲不是"质量更高的补充"，而是唯一能覆盖长尾知识点的通道**。这句写进 §2 的动机段，比"人工精讲质量更高"有力得多——因为它有数字，且数字是不可反驳的（全库只有 16 题）。

### 1.2 curated 解析规则（行式状态机）

```python
# 伪代码：curated 解析器
FIELDS = ["题目", "难度", "标签", "描述", "题解思路", "常见错误"]

def parse_curated(text: str):
    for seg_idx, seg in enumerate(text.split("---")):          # ① 先按分隔符切段
        seg = seg.strip().strip("\n")
        if not seg:                                            # ② 丢空段（实测 79→77，丢 2）
            report("D16_empty_segment", seg_idx); continue
        item, cur = {}, None
        for lineno, line in enumerate(seg.splitlines()):
            m = PREFIX_RE.match(line)                          # ③ 前缀式匹配，不依赖字段顺序
            if m and m.group(1) in FIELDS:
                cur = m.group(1)
                item[cur] = m.group(2).strip()                 # ④ 只按“第一个冒号”切分
            elif cur:                                          # ⑤ 无前缀行 = 上一字段续行
                item[cur] += ("\n" if cur in PARA_FIELDS else "") + line.strip()
        item["_locator"] = f"lines {first_line}..{last_line}"  # ⑥ INV-1 溯源
        yield item
```

| 规则编号 | 规则 | 依据 |
|---|---|---|
| P01 | 记录分隔符为**独占一行的** `---`；切分后 `strip()` 为空的段直接丢弃并计数 | 实测 79 段 / 77 条 |
| P02 | 字段识别用前缀正则 `^(题目|难度|标签|描述|题解思路|常见错误)：`，**不按位置**取字段 | 防手工编辑调换顺序 |
| P03 | 值切分只取**第一个全角冒号**；值内部允许出现冒号与箭头（如 `数值 → 下标`） | 实测正文含 `→`、`：` |
| P04 | `题解思路` / `常见错误` / `描述` 为**多行字段**，续行以 `\n` 拼接；其他字段续行以空格拼接 | 版式观察 |
| P05 | `标签` 按 `[,，、;]` 任一分隔符切分，逐项 `strip()`，丢弃空项，去重保序 | 实测仅英文逗号，但要容错 |
| P06 | `难度` 必须 ∈ `{简单, 中等, 困难}`，其他值 → `manual_queue(reason=D17_bad_difficulty)`，**不自动猜** | 三档是全局唯一定义域 |
| P07 | 每条记录记 `_locator = "lines {start}..{end}"`（1-based 行号区间） | INV-1 |
| P08 | 标题去重：`题目` 归一后若与已解析条目相同 → `manual_queue(dup_title)`，不自动合并 | 实测 0 重复，但手工追加会引入 |

#### 2.2.1 ET 错因线索改为 metadata，不进正文

原设计的「常见失分线索」段**从正文移除**，理由有二：① 主理人裁决三段式，正文不得出现复杂度/数据结构类断言，而 ET 线索容易被读成"本题错因"；② 04 要求正文 ≤300 字符，再插一段会挤掉考点拆解。

ET 信息不丢，改存 `metadata.et_hints`（≤2，规则见下表），由**诊断模块**在生成"错因解释"时按条目 ID 取用，检索侧也可用它做意图路由（用户问"为什么 TLE"时优先召回挂了 ET07 的条目）。

| 条件 | 挂载 ET（写入 `metadata.et_hints`） | 依据 |
|---|---|---|
| `tags` 含 动态规划 | ET13 DP 状态或转移错误 | ET13 定义 |
| `tags` 含 二分 / 三分 | ET08 死循环、ET10 边界条件遗漏 | 二分边界是本项目 S20 样本的实测错因 |
| `tags` 含 数学 / 数论 / 组合数学 / 位运算 | ET14 整数溢出 | ET14 定义 |
| `tags` 含 前缀和 / 差分 / 数组 | ET03 数组越界 | S01 样本（`pre` 开 n 却访问到 n） |

#### 2.6.1 `domain` 派生与 `points` 同域过滤（**数盘实测纠错，返工点**）

**必须用显式优先级表，不能取"第一个 tag 的 domain"。** 原因：CF API 返回的 `tags` 是**字母序**而非语义主次——按首个 tag 定域会把 `["dfs and similar","graphs"]` 判进"算法思想"，实测后果是图论只剩 2.2%、字符串只剩 0.8%。

**`domain` 规则：取该题所有 tag 的 domain 中 `prio` 最小者（最具体域优先）**

| prio | domain | 排序理由 |
|---|---|---|
| 1 | 计算几何 | 成员互斥且具体：被标 `geometry` 就几乎不可能是纯贪心 |
| 2 | 字符串 | 同上（`string suffix structures` 不可能与图论共主域） |
| 3 | 图论 | 同上 |
| 4 | 动态规划 | 同上 |
| 5 | 数据结构 | 同上 |
| 6 | 数学 | 泛但仍有明确成员 |
| 7 | 竞赛技巧 | 交互/通信/`*special` 类 |
| 8 | 算法思想 | **兜底类**：贪心/构造/分治/折半搜索，可与任何具体域共存 |
| 9 | 基础与实现 | **兜底类**：模拟/暴力/IO |

> 代码唯一事实来源：`crawler/taxonomy.py` 的 `DOMAIN_PRIORITY`。本表是文档镜像，**冲突时以代码为准**（主理人裁决）。
>
> 按此规则实测分布恢复合理：数学 21.5% / 图论 17.0% / 动态规划 14.8% / 算法思想 13.8% / 数据结构 9.1% / 字符串 8.5% / 基础与实现 7.3% / 计算几何 3.7% / 竞赛技巧 0.8%（CF 全库 11503）。

**`points` 规则：只取「与主域同域」的 tag 的 points，再去重、截前 3**

理由：`tree.json` 有 8 处跨域引用（如「动态规划/树形 DP」引用 `trees`），不限制会派生出**自相矛盾**的 domain/point 组合（主域判成图论、points 里却混进"贪心证明"）。

```python
def derive_domain_points(tags: list[str], tag_map: dict) -> tuple[str, list[str]]:
    # 1) 主域：所有 tag 的 domain 中 prio 最小者
    domains = [tag_map[t]["domain"] for t in tags if t in tag_map]
    if not domains:
        return "未分类", []
    domain = min(domains, key=lambda d: DOMAIN_PRIORITY[d])
    # 2) points：只擕与主域同域的 tag
    points, seen = [], set()
    for t in tags:
        rec = tag_map.get(t)
        if not rec or rec["domain"] != domain:
            continue
        for pt in rec["points"]:
            if pt in seen:
                continue
            # 3) 精确匹配，不做包含匹配：三分 ≠ 三分查找，FFT ≠ 多项式与卷积
            assert pt in TREE_POINTS, f"point 名未登记: {pt}"
            seen.add(pt); points.append(pt)
            if len(points) == 3:
                return domain, points
    return domain, points
```

> ⚠️ **`point` 必须精确匹配**：数盘给的名字有几处与直觉不同——`三分` 实际是 **`三分查找`**、`FFT/NTT` 实际是 **`多项式与卷积`**、`2-SAT` 实际是 **`强连通分量与 2-SAT`**。用 `in`/模糊匹配会静默落进 `未分类`。

**E. 落库拍平（数盘实测约束，不改会导致 Chroma 过滤失效）**

ChromaDB 的 `where` 对**嵌套字段支持差**，过滤条件必须能直接下发：

```python
# ❌ 嵌套：Chroma 无法直接 where
{"metadata": {"status": "published", "visibility": "public"}}
# ✅ 拍平到 chunk metadata 顶层
{"status": "published", "visibility": "public", "is_deleted": 0, "domain": "图论", ...}
```

**约定**：写入向量库前把 `metadata.*` 全部拍平到 chunk metadata 顶层（键名不变，冲突加 `meta_`）。拍平后按主理人定稿构造：

```python
where = {"$and": [
    {"status":     {"$eq": "published"}},
    {"visibility": {"$ne": "restricted"}},
]}
# is_deleted：若写入 metadata 则加 {"is_deleted": {"$eq": 0}}；
# 否则由 _visible(doc) 在**候选入口**逐条判（主理人已实现）
```

> ⚠️ **`sensitivity` 不进检索 WHERE**（主理人裁决，守库同意）：L2 是精讲默认级，放进 WHERE 要么恒真（当前 100% 为 L2）要么把精讲全废。`sensitivity` 改作**脱敏 / 导出门禁**，不参与召回过滤。
>
> ⚠️ **过滤点必须在候选入口**（召回时逐条跳过），**不是取回后剔除**——后者泄露已经发生，只是没展示出来。

### 2.8 "不编造"的边界（可写 / 禁写清单）

| ✅ 可以说（有数据支撑或明确标注为推定） | ❌ 不能说 |
|---|---|
| 官方 rating / difficulty 数值与来源 | "本题最优复杂度是 O(n log n)" |
| 官方 tags 与其中文映射 | "先把数组排序，然后用双指针从两端扫描" 之类的**题解步骤** |
| 由 index+contest 前缀推定的粗标签（标 medium/low） | "本题考察单调栈"（AtCoder 无标签时的**断言式**考点陈述） |
| "同难度档、同标签的题目通常需要注意 X"（ET 线索，标"非本题统计"） | "本题有 62% 的提交因溢出 WA"（编造的统计） |
| AC 数、题位、赛事类型等可直接读取的元数据 | 题面原文、样例输入输出、约束范围（未获授权且未抓取） |
| "建议先做同场 A 题"（基于赛制结构的训练建议） | "本题难度相当于 LeetCode 中等"（跨平台未标定的等价断言） |

> **实现层的强制手段**：门禁 G3b 对 `entry_type=hint` 的正文做**黑名单正则扫描**，命中即 reject（G3c 另查题面复述）：
> `O\([^)]*\)`（复杂度记号）、`题解`、`思路是`、`样例`、`输入格式`、`输出格式如下`、`数据范围`、`1e[0-9]`、`10\^[0-9]`、`%`（提交占比）。

### 2.9 引用外观与生成层降级话术（`entry_type` 的唯一用途）

`entry_type` 存在的理由只有一个：**让"考点提示"永远不被当成"题解"**。如果两类条目用同一种引用外观，学生和生成模型都会把 `hint` 条目当解法用，§2.8 守住的边界会在生成层被破掉。

| 条目类型 | 引用外观（04 渲染） | 生成层约束（写进 system prompt） |
|---|---|---|
| `entry_type=solution`（题解卡） | `[1] 01背包（精讲 · 中等 · 动态规划/背包）` | 可据此展开解法、复杂度、代码 |
| `entry_type=hint`（爬取 8500） | `[1] CF1A（考点提示 · 简单 · 数学/向上取整）` | **只可描述考查方向与典型套路，不得据此推断复杂度或数据结构选择** |

**降级话术模板**（01 答辩时现场对比用，两句话必须明显不同）

| 场景 | 话术 | 身份 |
|---|---|---|
| 命中 curated | "这道题的标准做法是……（依据精讲条目 `curated-05`）" | 讲题者 |
| 命中 meta | "这道题属于「动态规划 / 背包」方向、难度简单，建议先做同档同标签的 X 题；**具体解法我这边没有可引用的精讲，不能替你写**，可以先说说你的思路" | 引导者 |

> **`meta` 条目在正文里必须自带边界声明**（G3b 强制）：`【信息边界】仅含官方元数据与标签映射，无题面原文、题解与复杂度结论`。这句话不是客套，是给生成层的可视锚点——prompt 里可以写"若引用条目的正文含【信息边界】声明，则禁止输出解法细节"，模型有据可依，比抽象规则更稳。

## 3. 切片（Chunking）策略

### 3.1 判定阈值

| 正文 `char_len` | 切片方式 | 产出块数 | 重叠 | 适用对象（实测） |
|---|---|---|---|---|
| **≤ 600** | 整条入库，`chunk_type="whole"` | 1 | 0 | **当前全部条目都落此档**：curated 77 条（≤422）+ crawled 三段式（160–400） |
| **601 – 1200** | 按段落（`【】`标记）切，整段不切断；单段 > 400 时在句号处二次切 | 2–3 | 80 字符 | **19 条新增知识卡中 6 条 > 600 字符，尚未二次切片**（规则已定、待执行） |
| **> 1200** | 强制拆分 + 父子块（`parent_doc_id` 指回整条），子块 ≤ 600 | ≥3 | 80 字符 | 未来长文本（当前无） |
| **< 120 或 > 500（crawled）** | 不入库，退配合成 | 0 | — | 门禁 G2 拦截（301–500 只告警） |

> **阈值 600 的依据**：curated 实测 p75=262、max=422；crawled 三段式按 §2.2 目标 160–300（硬上限 500，301–500 告警）。取 600 = 最长的 1.4 倍余量。**更硬的约束来自 embedding**：04 用 `bge-small-zh-v1.5`，最大序列 512 token，超长会被**静默截断**（丢内容且不报错）。中文 1 字 ≈ 0.7–1 token，600 字符 ≈ 420–600 token 已贴边，所以**实际安全上限取 500 字符**（≈350–500 token），并在 04 侧按 token 复核一次。
>
> **结论（按主理人实测口径，2026-11-07 定稿）**：
> - **存量精讲 77 条 100% 单块**（实测 p25=208 / 中位 236 / max 422）；
> - **19 条新增知识卡中有 6 条超 600 字符**，**尚未二次切片**（切片规则已定、待执行）；
> - **爬取 8500 条全部单块**（三段式 160–300 字符）；
> - **当前索引 8,558 块；按规则切完这 6 条后约 8,564 块**（+6）。
>
> 因此正确表述是"**存量 77 条 100% 单块；19 条新增卡中 6 条超 600 字符，尚未二次切片**"——**不能写"精讲库 100% 单块"，也不能写"已切"**（索引层面还没做这件事）。答辩被抽到一条被切开的卡片时，前后说法必须一致。
>
> **`601–1200` 档实际只会出现这 6 条（< 100 条）**，按 04 的建议**不建父链**：两段各自独立入库、不挂 `prev/next`、不做父块回填。父子块机制保留为二期长题解语料的预案（§3.3 去重键仍然必须实现，属于防御性实现）。

**按 token 复核（04 要求 ≤480 token、重叠 80 token）**

| 正文类型 | 字符上限 | 估算 token | 结论 |
|---|---|---|---|
| curated 精讲 | 422（实测 max） | ~300–420 | ✅ 安全 |
| crawled 三段式 | 400（门禁上限） | ~280–400 | ✅ 安全 |
| 假设的 600 字符长条目 | 600 | ~420–600 | ⚠️ 临界，故 §3.1 把安全上限收到 500 |

### 3.2 切片 id 规则

```
doc_id     = problem_id                       # cf-1A / atcoder-abc042_b / curated-01
chunk_id   = f"{doc_id}::c{seq:02d}"          # cf-1A::c01 ; atcoder-abc042_b::c01
parent_doc_id = doc_id                        # 多块时用于父块回填；单块时 = doc_id
slice_idx  = 0                                # 单块恒 0；04 用它限制"同题最多留 2 条相邻切片"
```

| 字段 | 单块 | 多块 |
|---|---|---|
| `chunk_type` | `whole` | `head` / `body` / `tail` |
| `slice_idx` | 0 | 0..n-1 |
| `prev_chunk_id` / `next_chunk_id` | — | 相邻链，支持上下文扩展召回 |
| `char_len` | = 正文长度 | 单块长度 |
| `offset_start` / `offset_end` | 0 / len | 原文字符偏移（INV-1 精确到字符） |

> **重要**：`chunk_id` 里**不含内容哈希**，否则内容微调会变成新块、旧向量永久残留。内容变化通过 `content_hash` 字段做"是否重嵌入"的判定（§7.2），`chunk_id` 保持稳定。

### 3.3 检索期去重键（交付给 04）

## 4. 难度归一化

### 4.1 五档（存储）+ 三档（展示/硬过滤）+ 五档中文名 三轨制

五档切点**采用主理人与数盘核定的 `cf_tier()` 口径**（`crawler/taxonomy.py` 为唯一事实来源），不是我自己拍的 1450 分档——CF 的 `rating` 是**赛后 Elo**，语义必须靠映射表定义，不能按分数直觉切。

| 档位 | `difficulty_level` | Codeforces `rating` | AtCoder `difficulty` | `difficulty`（三档，展示） | 能力画像 |
|---|---|---|---|---|---|
| **L1** | 入门 | `< 1200` | `< 200` | 简单 | 语法 + 循环 + 数组基本操作 |
| **L2** | 简单 | `1200 – 1399` | `200 – 599` | 简单 | 排序/贪心/简单 DP/二分入门 |
| **L3** | 中等 | `1400 – 1699` | `600 – 1299` | 中等 | 图论基础、DP 建模、数据结构 |
| **L4** | 较难 | `1700 – 1999` | `1300 – 1999` | 困难 | 树结构、复杂 DP、组合计数 |
| **L5** | 困难 | `≥ 2000` | `≥ 2000` | 困难 | 高级数据结构、构造、数学专项 |

```python
def cf_tier(rating):               # rating: int | None —— 主理人/数盘核定口径
    if rating is None: return None
    if rating < 1200: return "L1"
    if rating < 1400: return "L2"
    if rating < 1700: return "L3"
    if rating < 2000: return "L4"
    return "L5"

def ac_tier(difficulty_raw):       # 可能为负（D07 clamp 后传入）
    if difficulty_raw is None: return None
    d = max(0, difficulty_raw)
    if d < 200:  return "L1"
    if d < 600:  return "L2"
    if d < 1300: return "L3"
    if d < 2000: return "L4"
    return "L5"
```

## 5. 去重与归一

### 5.1 标题归一算法（用于"疑似同题"判定，**不用于改写 `title`**）

| 步骤 | 操作 | 示例 |
|---|---|---|
| 1 | Unicode `NFC` 归一 | `e` + `´` → `é` |
| 2 | 删零宽字符 `\u200b`–`\u200d`、`\ufeff` | — |
| 3 | 全角转半角（ASCII 区） | `ＡＢＣ` → `ABC` |
| 4 | 统一小写 `lower()` | `Theatre Square` → `theatre square` |
| 5 | 去掉**开头**冠词 `the / a / an`（只去开头，不动中间） | `The Beaver's Problem - 3` → `beaver's problem - 3` |
| 6 | 去掉题位/版本前缀 `^[A-Z][0-9]?\.\s*`、`^Problem\s+` | `A. Product` → `product` |
| 7 | 删除标点（保留字母数字与空格） | `What a SauSaGe! It's All Meat` → `what a sausage its all meat` |
| 8 | 空白折叠为单空格 + `strip()` | — |
| 9 | 计算 `title_norm` + `title_hash = md5(title_norm)` | — |

> ⚠️ **不要做**：词形还原（lemmatize）、同义词替换、删除 `(Hard Version)` / `(Easy Version)` 后缀。实测 CF 中 `X (Easy Version)` 与 `X (Hard Version)` 是**两道不同题**（不同 rating、不同 `problem_id`），合并会直接丢题。`(Hard Version)` 差异保留在 `metadata.version_suffix` 供关联展示。

### 5.2 `problem_id` 规范（全局唯一键，采纳 04 提案 + 2 处修正）

| 平台 | 格式 | 示例 | 说明 |
|---|---|---|---|
| Codeforces | `cf-{contestId}{index}` | `cf-1A`、`cf-1883F`、`cf-1202A1` | 实测 0 重复（`(contestId,index)` 唯一） |
| AtCoder | `atcoder-{task_id}` | `atcoder-abc042_b`、`atcoder-abc232_f` | **修正 04 的 `atcoder-{contest_id}_{task}`**，理由见下 |
| curated | `curated-{序号:02d}` | `curated-01` | **修正 04 的 `curated-{slug}`**，理由见下 |

> **修正 1（AtCoder 不能用 `contest_id`）**：实测 **4379 条**的 `contest_id` 与 `id` 首段不一致，例如 `id=abc232_f` 的 `contest_id` 是 `adt_hard_20240206_1`、`id=1202Contest_a` 的 `contest_id` 是 `DEGwer2023`。若按 `{contest_id}_{task}` 生成，会得到 `atcoder-adt_hard_20240206_1_abc232_f` 这种又长又随社区镜像变化的键；而 **`task_id` 本身全局唯一且稳定**，直接用 `atcoder-{task_id}`，`contest_id` 只用于拼 URL。
>
> **修正 2（curated 不用 slug）**：中文标题的 slug 需要拼音转换，且标题一改 slug 就变、幂等失效（§5.3 的 upsert 会变成新增而非覆盖）。改用**解析序号**：序号一经分配不得变更，标题随便改键都不变。拼音 slug 仍生成，但只存 `metadata.slug` 供 URL/前端路由用，不做主键。

> **不要用 title 的 hash 做 `problem_id`**（04 已明确指出）：中文题名存在 `01背包` / `0-1 背包` 变体，hash 会把同一题拆成两条。

### 5.3 同一题多来源 / 多次爬取的处理

| 情形 | 判定 | 处理 |
|---|---|---|
| 同一快照内 `problem_id` 重复 | 实测 0 | 保留 `solvedCount` 最大的一条，其余丢弃，`dup_in_snapshot += 1` |
| 跨快照重爬（同一 `problem_id`） | `content_hash` 相同 | **no-op**（不重嵌入、不升版本），仅更新 `last_seen_at` |
| 跨快照重爬 | `content_hash` 不同 | **覆盖写**，`version += 1`，旧向量按 `chunk_id` 覆盖（同 id 替换） |
| 同名不同题（399 组） | `problem_id` 不同 | 全部保留，写 `same_name_count` 与 `same_name_group`，检索时作"易混淆"提示 |
| curated 与 crawled **疑似同题** | `title_norm` 完全相等 **且** 三档难度相等 | **不自动合并**！生成 `candidate_link` 记录进人工队列；确认后写 `metadata.related_doc_id`，检索时做"精讲 + 原题"配对展示 |
| curated 与 crawled 标题相近但不相等 | 不做任何自动动作 | 只依赖向量召回的语义相似，不做规则合并 |

> **为什么不自动合并 curated 与 crawled**：curated 条目是**知识点级**精讲（如"两数之和"是通用题名，不同 OJ 各有同名题），crawled 是**题目实例**。两者是"讲解-实例"关系，不是重复关系。合并会破坏"一个知识点挂多道练习题"的结构。这条规则要在 04 检索与 RAG 调优做"相似题关联"时遵守。

### 5.4 内容指纹

```
content_hash = sha256(content_text.encode("utf-8")).hexdigest()   # 对 content 原文，不含 metadata
```
用途：① 判断是否需要重嵌入；② 检测"模板退化"（大量条目 hash 相同 = 模板槽位没填进去，属严重缺陷，门禁 G8b 拦截）。

| 层级 | 定义 | 取值 | 说明 |
|---|---|---|---|
| 批次 `batch_id` | 一次完整跑批 | `{yyyymmdd}-{source}-{mode}`，如 `20261107-cf-full` | 与快照绑定 |
| 分片 `shard_id` | 批次内按 `problem_id` 哈希切 | `shard_size = 500`（CF 11503 → 24 片；AC 9900 → 20 片） | 分片数固定，便于并行与续跑 |
| 阶段 `stage` | `parse / normalize / synthesize / chunk / gate / embed / upsert` | 7 个 | 阶段间通过中间态表解耦 |

```python
shard_of = lambda key: int(md5(key.encode()).hexdigest(), 16) % N_SHARDS
```
> 用**哈希分片而非顺序切分**：新增题目不会导致所有分片位移，续跑定位稳定。

### 7.2 幂等（upsert 键）

| 存储 | 键 | 冲突动作 |
|---|---|---|
| 文档表（元数据） | `problem_id` | `INSERT ... ON CONFLICT(problem_id) DO UPDATE`，`version = version + 1`（仅当 `content_hash` 变化） |
| 块表 | `chunk_id` | 同上；`content_hash` 未变则跳过 |
| 向量库（如 Chroma/Milvus） | `chunk_id` 作为 primary key | 先 `upsert(vector, metadata, id=chunk_id)`；`content_hash` 未变则**不重嵌入**（省 embedding 成本） |
| 批次账本 | `(batch_id, stage, shard_id)` | 记录状态与游标，重跑从 `failed`/`pending` 片开始 |

**幂等的验收方式**：同一快照连跑两次，第二次必须满足 `inserted=0, updated=0, no_op=全部, 库内总条数不变`。这是 §8 抽检的一条硬指标。

### 7.3 断点续跑

```python
# checkpoint 表：(batch_id, stage, shard_id) -> status, cursor, updated_at
for shard in shards:                       # 24 片
    ck = load_checkpoint(batch_id, stage, shard)
    if ck.status == "done":                # 已完成 → 跳过（续跑核心）
        continue
    items = read_shard(shard, offset=ck.cursor)   # 从游标继续，不从头
    for i, it in enumerate(items):
        process(it)
        save_checkpoint(batch_id, stage, shard, cursor=ck.cursor + i + 1)
```

| 断点粒度 | 为何不用更细/更粗 |
|---|---|
| **分片级 + 分片内游标**（每 50 条落一次盘） | 单条级太频繁（IO 放大）；只到分片级则一片重跑损失 500 条 |
| 进程被杀（Ctrl+C / OOM） | 重新执行同一 `batch_id` 的同一 `stage` 即续跑，不产生重复数据（依赖 §7.2 幂等） |

### 7.4 失败重试

| 异常类型 | 例子 | 可重试 | 策略 |
|---|---|---|---|
| 网络/限流 | 连接超时、HTTP 429、5xx | ✅ | 指数退避 `1s → 2s → 4s`（±20% 抖动），最多 3 次；全失败 → `dead_letter` |
| 解析异常 | JSON 结构变化、字段类型不符 | ❌ | 直接进 `dead_letter`，整批告警（说明源改了契约） |
| 门禁 reject | G1–G10 | ❌ | 记 `gate_report`，不重试（重试也不会通过） |
| 向量库写失败 | 超时、维度不符 | ✅（维度不符除外） | 同网络策略；维度不符视为配置错误，整批中止 |
| 快照文件缺失 | `FileNotFoundError` | ❌ | 整批中止并提示先跑 S0 |

> **不重试门禁失败**是刻意设计：门禁失败代表数据缺陷，重试只会放大日志。修复路径是"改规则/补数据 + 重跑该分片"。

| 字段 | 层级 | 含义 |
|---|---|---|
| `batch_id` / `stage` / `shard_id` | 分片 | 定位坐标 |
| `in_count` / `out_count` | 分片 | 进入 / 产出条数（`out < in` 说明有损，需解释） |
| `reject_count` / `degrade_count` / `manual_count` | 分片 | 三分流计数 |

### 7.6 端到端伪代码

```python
def run_batch(snapshot, mode="full"):
    batch_id = f"{today}-{snapshot.source}-{mode}"
    for stage in ["parse","normalize","synthesize","chunk","gate","embed","upsert"]:
        for shard in range(N_SHARDS):
            if checkpoint_done(batch_id, stage, shard): continue
            raw = read_shard(snapshot, shard)
            for item in raw:
                try:
                    out = STAGES[stage](item)
                    if out.rejected: record_reject(batch_id, stage, out); continue
                    write_stage_table(stage, out)          # 幂等 upsert by problem_id/chunk_id
                except Retryable as e:
                    retry_with_backoff(lambda: STAGES[stage](item), e, max_tries=3)
                except Exception as e:
                    dead_letter(batch_id, stage, item, e)
            save_checkpoint(batch_id, stage, shard, "done")
    emit_report(batch_id)                                   # §6.3
```

### 7.7 状态机与检索侧过滤钩子（守库 §6 硬约束）

**状态机**：`draft → reviewing → published → retired`。**只有 `published` 允许写向量库并在检索中可见**。

| 状态 | 谁置位 | 允许的下一步 | 说明 |
|---|---|---|---|
| `draft` | 合成/门禁 G3c 命中 | `reviewing` / 直接 `retired` | 摘要疑似复述题面、正文偏薄等都先落这里 |
| `reviewing` | 人工复核 | `published` / `retired` | 人工队列（§6.2 manual 流） |
| `published` | 人工或全绿门禁自动 | `retired` | 进 chroma + 元数据库 |
| `retired` | 权利人投诉 / 站方要求 / 内容过期 | — | **必须同时从 chroma 删除**；SQLite 侧 `PRAGMA secure_delete=ON` + `VACUUM` |

**两个出口都必须过滤**（守库裁决：只做一个出口等于没做）

| 出口 | 过滤规则 | 漏掉的后果 |
|---|---|---|
| ① **检索响应**（返回给学生的结果） | 四条件（见下） | 学生直接看到内部独家题解——**即使没送 LLM，也已经泄露** |
| ② **prompt 组装**（送 LLM 的上下文） | 同上，**且 fail-closed**（配置缺失/异常默认剔除，不得默认放行） | 内容外流给第三方模型 |

```python
STRICT = {"status": None, "visibility": "restricted", "is_deleted": 1}

def _safe(db_val, key):
    # fail-closed：字段缺失取最严格默认值，绝不默认放行
    return STRICT[key] if db_val is None else db_val

def _visible(doc):          # 候选入口逐条判（召回时跳过，不是取回后剔除）
    return (_safe(doc.get("is_deleted"), "is_deleted") == 0
            and _safe(doc.get("status"), "status") == "published"
            and _safe(doc.get("visibility"), "visibility") != "restricted")
```

- **出口① 检索响应** 与 **出口② prompt 组装** 共用 `_visible()`，避免两处实现漂移；
- **`sensitivity` 不参与召回过滤**（主理人裁决）——它只在**脱敏 / 导出**环节作门禁；
- 过滤点必须在**候选入口**：召回时逐条跳过，不能"先取回再剔除"（后者泄露已经发生）。

> **`is_deleted` 是第一条件**（数盘/守库共同指出）：`knowledge_items` 有软删列，前三条件漏掉它会导致**已删除条目被检索命中**。

**必须有的单测**（这是唯一能证明"真的隔离了"的东西，比文档写十行有用）：

```python
def test_restricted_never_leaks():
    item = make_item(visibility="restricted", status="published", sensitivity="L1")
    assert item not in retrieve("任意 query")          # 出口①
    assert item not in build_prompt_context("任意 query")  # 出口②

def test_fail_closed_on_missing_fields():
    item = make_item_without(["status", "visibility", "is_deleted"])
    assert item not in retrieve("任意 query")          # 缺字段必须被剔除，不是放行
```

`admin` 检索到 `restricted` 条目时写审计（`KB_READ_RESTRICTED`，WARN），敏感内容每次访问留痕。

| 钩子字段 | 取值 | 谁消费 |
|---|---|---|
| `status` | `draft/reviewing/published/retired` | 03 写入侧 + 04 检索侧双层校验 |
| `visibility` | `public/internal/restricted` | 04 结果组装（`restricted` 直接丢弃） |
| `sensitivity` | `L1`–`L4` | 04 结果组装（按用户 scope 比对） |

> **为什么要双层校验**：写入侧门禁负责"不该入库的不入库"，检索侧钩子负责"入库了也不该给这个用户看"。单层都会漏——权限变更、密级上调都发生在入库之后。

**删除响应（一键清理）**

```bash
scripts/purge_source.py --source cf           # 删该来源全部条目：文档表 + 块表 + chroma + 缓存
scripts/purge_source.py --problem-id cf-1A --hard     # 单条彻底删除（配合 secure_delete + VACUUM）
```

产物：删除前的清单快照（`problem_id` 列表 + 条数 + 哈希）写入审计表，供事后证明"已删干净"。

### 7.8 增量幂等在 S1 是否可用（答复 01 的排期耦合）

**可用，且是 S1 就能用的**：增量能力不依赖全量跑通，只依赖三件事，三件事在 §7.2/§7.3 已定型——

| 条件 | 状态 | 说明 |
|---|---|---|
| `problem_id` 稳定（不随标题/批次变化） | ✅ 已定 | §5.2：`cf-{contestId}{index}` / `atcoder-{task_id}` / `curated-{序号}`，均与标题解耦 |
| 键级 upsert + `content_hash` 短路 | ✅ 已定 | 哈希不变 → 不重嵌入、不升版本，只更新 `last_seen_at` |
| 分片 checkpoint 续跑 | ✅ 已定 | `(batch_id, stage, shard_id) → status, cursor`，可断点续 |

**因此 01 的排期（S1 出 3000 条 → S3 补到 8000+）成立**，具体跑法：

| 阶段 | 动作 | 产出 |
|---|---|---|
| S1（第 4–6 周） | 先跑 curated 77 → 再跑 CF `rating ≤ 1999` 的前 3000 条（按 `solvedCount` 降序取热门题，保证"够用且好查"） | 3000+ 条可用语料，`status=published` |
| S1 末~S3 | 同一 `batch_id` 加 `--resume`，按 §0.4.5 配额补齐 CF 至 6000、AC 至 2500 | 8500 条（+精讲 120 = 8620） |
| S3 之后 | 二期放开 `rating ≤ 2399` 与 ARC/AGC | 16000+ 条 |

> **增量不会产生重复**：同一 `problem_id` 二次入库走 `ON CONFLICT DO UPDATE`，`content_hash` 相同则 `no_op`。这一点必须在 S1 的验收里跑一次（同批次连跑两次，`no_op_rate` 必须 = 100%），否则"S3 补量"会变成"数据翻倍"。

## 8. 质量抽检方案

### 8.1 抽样设计

| 项 | 设计 | 理由 |
|---|---|---|
| 抽样量 | **每批次 100 条**（库容 < 10k 时）；库容 ≥ 10k 后 **200 条** | 100 条二项分布下，合格率 90% 时 95% 置信区间 ≈ ±6% |
| 抽样方式 | **分层抽样**：按 `source`（curated/CF/AC）× `difficulty`（简单/中等/困难/未知）× `tags` 高频 Top10 三层配额 | 纯随机抽样会漏掉低频但高风险的组合（如 AtCoder `difficulty=未知`） |
| 配额示例 | curated 20 / CF 45 / AC 35；其中强制包含 `difficulty=未知` 10 条、`tags_inferred=true` 15 条、`difficulty_clamped=true` 3 条、`degrade` 状态 15 条 | 高风险样本加权 |
| 抽样脚本要求 | 结果固定（种子 = `batch_id`），可复现 | 便于回归对比 |

### 8.2 检查指标与合格线

### 11.1 ④ `entry_type` 判定规则（用于给 120 条精讲打标）

**值域定稿（主理人签约）：中文四值**，代码内枚举用英文，二者固定一一映射（`card_kind` 不进检索，已废弃）。

| `entry_type`（文档/DB 值） | 代码枚举 | 特征 | 谁产出 | 04 的 `w_type` |
|---|---|---|---|---|
| **题解** | `solution` | 对应**唯一一道 OJ 题**，含题解思路与常见错误 | 人工（存量 77 中一部分） | 1.25 |
| **知识点卡** | `concept` | 讲**一类题**的通用做法/模板，不对应具体题 | 人工（新增卡 + 存量一部分） | 1.15 |
| **元知识** | `strategy` | 赛制/训练/罚时等策略，不含算法内容 | 人工 | 1.15 |
| **考点提示** | `hint` | 由**官方元数据 + 标签映射**生成，无题解、无复杂度结论 | 机器（8500 条爬取） | 1.0 |

> **没有第 5 个值"题面摘要"**（主理人裁决）：它与"考点提示"在数据上是同一形态——都是无题解的依据性内容；多一个值只会让分类边界变模糊。

**判定决策树（按顺序判，命中即停）**

| 序号 | 判定条件 | `entry_type` | 例 |
|---|---|---|---|
| 1 | 正文含"题解思路/常见错误"且**能对应到唯一一道 OJ 题**（题名可查或标了 `problem_id`） | 题解（`solution`） | 「两数之和」「01背包」 |
| 2 | 讲**一类题的通用做法**，不对应具体 OJ 题，含模板要点或判别信号 | 知识点卡（`concept`） | 「并查集」「线段树」「网络流」「后缀数组」 |
| 3 | 讲**比赛/训练/策略**，不含算法内容 | 元知识（`strategy`） | 「ICPC 赛制与训练建议」「赛时策略与罚时管理」 |
| 4 | 正文由**官方元数据 + 标签映射**生成，无题解、无复杂度结论 | 考点提示（`hint`） | 「CF1A 考点提示」 |
| 5 | 以上都不满足（含题面原文、含未验证断言、来源不明） | **不产出条目**，进 `manual_queue` | — |

> **为什么存量 77 条里大量落在 `concept` 而非 `solution`**：它们标题写作"题目：并查集"，但内容是模板与判别信号，不是某道 OJ 题的解法。用 `concept` 区分开，04 才能做意图路由："用户问某道具体的题 → 优先 `solution`"、"问怎么做某类题 → 优先 `concept`"。

| `hint` | `metadata` | `crawled` | `platform` |

## 12. 落库实况与 DB 写入契约（**前置条件：字段不落库，前三节全部作废**）

> ⚠️ 守库与数盘各自核对 `src/acm_coach/db/models.py::KnowledgeItem`（第 96–124 行）后确认：**文档里承诺的 11 个合规字段，库表里一个都没有**。`knowledge_items` 现有列只有：
> `id / title / difficulty / rating / tags / domain / source / url / content / content_hash / chunk_index / quality_score / is_deleted`
> 而 `db/session.py::_ensure_columns` 的轻量迁移只覆盖 `users` / `chat_sessions` / `messages`，**不含 `knowledge_items`**。
>
> 后果：G9 的"出处字段非空 + 枚举校验"、G10 的"只有 published 进向量库"、R6 的四条件过滤，**在库表层面无处落地**——门禁在内存对象上校验通过，一写 DB 就丢字段。这是"文档承诺、代码没有"的典型翻车点，评委拿模型文件一对就发现合规字段只活在文档里。

### 12.1 两层落库方案（守库 §6.7 定稿）

不把 11 个字段全加成列，分两层：

```python
# 加到 db/session.py::_ensure_columns 的 additions 字典
"knowledge_items": {
    "status":         "TEXT DEFAULT 'published'",   # draft/reviewing/published/retired
    "visibility":     "TEXT DEFAULT 'internal'",    # public/internal/restricted
    "sensitivity":    "TEXT DEFAULT 'L2'",          # L1/L2/L3/L4
    "retention_days": "INTEGER DEFAULT 0",
    "meta_json":      "TEXT",                       # license/fetched_at/entry_type/processed_by/mirror/points
},
```

| 层 | 字段 | 落位 | 理由 |
|---|---|---|---|
| **控制字段**（参与 `WHERE`） | `status` / `visibility` / `sensitivity` / `retention_days` | 各建列，前两个建索引 | 四条件过滤要在 SQL 里做，塞进 JSON 就没法用索引 |
| **溯源字段**（只展示/审计） | `license` / `fetched_at` / `entry_type` / `processed_by` / `mirror` / `points` | 统一 `meta_json` 一列 | 少 5 次 ALTER、模型不膨胀；**但门禁仍在写入前校验**（不能"只存不管"） |

### 12.2 `meta_json` 键名契约（定稿，别自创键名）

```json
{
  "content_origin": "metadata",
  "entry_type":     "solution | concept | strategy | hint",
  "processed_by":   "platform | human",
```

### 12.3 6 处结构性错配与修法（数盘 §5.5.1）

| 本文字段 | DB 实况 | 写入侧动作 |
|---|---|---|
| `tags`（数组） | `tags: String(255)`，**逗号分隔串** | 写入前 `",".join(tags_zh)`，按中文名累加、**超 200 字符即裁剪并置 `meta_json.tags_truncated=true`**（200 而非 255：留余量，中文标签 6 个就可能 60+ 字符） |
| `url` / `origin_url` | 列名只有 **`url`** | **保持 `url` 不改名**（改名要动 repositories + 迁移，成本不对等）；`origin_url` 只作 `meta_json` 别名 |
| `content` | `content: Text` 单列 | 放**自写正文/摘要（≤500 字符）**；**绝不写题面全文**（落库字段白名单里就没有题面） |
| `points`（≤3 个知识点） | **无对应列** | 写 `meta_json.points`（JSON 数组）。**不要拼进 `tags`**——`tags` 供 BM25 用，混入知识点名会污染字段权重 |
| `slice_idx` / 总块数 | 只有 **`chunk_index`**，无 `chunk_count` | 同 `id` 多行、`chunk_index` 递增；总块数用 `COUNT(*) GROUP BY id` 求，**不要当成同名字段互填** |
| `source` | 默认值 `"manual"` | 取值统一为 **`curated` / `cf` / `atcoder` / `manual`**；其中 **`manual` = UI 人工录入**、**`curated` = 语料文件导入**，**是两回事、不能互相映射**（否则吞掉来源差异）。写入时显式给值 |

### 12.4 四条件过滤（不是三条件）

```sql
WHERE is_deleted = 0
  AND status = 'published'
  AND visibility != 'restricted'
```

> **`is_deleted` 必须挡**（数盘）：索引是快照，删条目不会自动重建，快照里仍留着已删条目 → 不挡就会**被检索命中**。落 Chroma metadata 时同带 `is_deleted`，或由 `_visible(doc)` 在候选入口判（主理人已实现后者）。
>
> **`sensitivity` 已从检索 WHERE 移除**（主理人裁决）：L2 是精讲默认级，放进 WHERE 要么恒真要么全废；改作**脱敏 / 导出门禁**。

### 12.5 `source` / `mirror` / `license` 三维度不能合并（守库裁决）

| 字段 | 回答的问题 | 取值 |
|---|---|---|
| `source` | 数据**从哪个站点来的**（权利主体是谁） | `curated`（文件导入）/ `cf` / `atcoder` / `manual`（UI 录入） |
| `mirror` | 经由**哪个通道/镜像**拿到 | `kenkoooo`（AtCoder）/ 空（直连官方 API） |
| `license` | 受**哪份条款**约束 | `Codeforces-Terms` / `AtCoder-Terms` / `CC-BY-NC-SA-4.0` / `internal-only` |

> **为什么不能合并**：若 AtCoder 主张删除，我们必须知道**权利主体是 AtCoder**（走 AtCoder-Terms 流程），而"数据是从 kenkoooo 镜像拿的"只影响**该停哪个通道**。把 `source` 写成 `kenkoooo` 会让权利主体在库里消失，删除响应就找错对象。所以三个都写。
