## 2. 认证与会话

### 2.1 口令策略

| 项 | v3 现状 | v4 规则（★=与当前实现存在差异，需改代码） | 优先级 |
|---|---|---|---|
| 最短长度 | 注册校验 ≥6 位 | 已实现：`password_strength()` ≥8 位且字母+数字必含 | 已达标 |
| 复杂度 | 无 | 已实现：字母+数字必含（≥12 位策略视实现成本决定是否加） | 已达标 |
| 弱口令黑名单 | 无 | top-1000 弱口令表 + 禁止与用户名相似（编辑距离/包含关系） | 【建议】 |
| 默认口令 | `admin / admin123` 长期存在 | **首次启动强制改密**：`must_change_password=1`，改密前只允许访问 `/api/auth/password` | 【必做】 |
| 哈希算法 | 单一 PBKDF2-SHA256 实现，v3 迭代 20 万次 | 算法不变；**迭代数已整改为 600,000**（原 260,000），并加 `needs_rehash()` 在登录成功后无感升级旧哈希 | ✅ 已整改 |
| 盐 | 16B 随机（`secrets.token_hex(16)`） | 保持 16B，每用户独立 | 已达标 |
| 存储格式 | `pbkdf2_sha256$200000$salt$hash` | 保持自描述格式（迭代数写在串里，便于平滑升参数） | 已达标 |
| 比较方式 | `hmac.compare_digest` | 保持（防时序侧信道） | 已达标 |
| 口令传输 | Streamlit 表单（本地回环） | 仅在 TLS 或 `localhost` 下提交；禁止把口令写进 URL/日志 | 【必做】 |
| 改密后动作 | 无 | `token_version += 1`（该用户全部会话的旧 token 立即失效）+ 写 `AUTH_PASSWORD_CHANGE` 审计 | 【必做】 |
| 管理角色长度 | — | `admin`/`auditor` 建号时 ≥12 位（账号数极少，成本为零） | 【建议】 |

**迭代数 20 万 → 60 万的定档依据（答辩可直接用这组数回答"为什么定 60 万"）**

| 迭代数 | 单次校验耗时（i5 级 CPU 量级） | 对本系统的影响 | 对离线爆破的影响 |
|---|---|---|---|
| 200,000（v3） | ≈0.06 s | 无感 | 基线 |
| 260,000（整改前） | ≈0.08 s | 无感 | 提升 30% |
| **600,000（现行值）** | **≈0.18 s** | 登录慢 0.1 s，全套流程无感 | **提升 3 倍** |

结论：本系统用户规模是"班级/个人"级（日活 ≤ 50），600,000 带来的 0.1 秒完全不影响体验，但对"数据库被拖走后离线爆破"的抵抗提升 3 倍。**这是全案性价比最高的一处改动，改的只是配置默认值一行。**

> 兼容性：`verify_password()` 从存储串里读迭代数，所以旧哈希（20 万次）仍能校验；登录成功后判断迭代数 < 600,000 即用新参数重写（`needs_rehash()`），属无感升级。

```python
# v4 口令哈希：沿用 v3 的存储格式，只提升迭代数（配置项，不改算法）
PBKDF2_ITERATIONS = 600_000

def needs_rehash(stored: str) -> bool:
    algo, iters, *_ = stored.split("$")
    return algo != "pbkdf2_sha256" or int(iters) < PBKDF2_ITERATIONS

# 登录成功后：if needs_rehash(row["password_hash"]): 用新参数重写该行
```

### 2.2 JWT 结构

**v4 只签发一种令牌：access token。** 不引入 refresh token（理由与取舍见 §2.3、§2.4），这是由**部署形态**决定的（Streamlit 服务端代理，浏览器不持有令牌）。

| 段 | 字段 | 取值 | 说明 |
|---|---|---|---|
| Header | `alg` | `HS256` | 对称签名，密钥 `JWT_SECRET`（`config.resolve_secret_key()`） |
| Header | `typ` | `JWT` | |
| Header | `kid` | 目前未设置 | 为将来密钥轮换预留，加不加都不影响 |
| Payload | `iss` | **`acm-coach`** | 与当前实现一致；`decode_token()` 已强制校验 `issuer` 与 `require: [exp, sub]` |
| Payload | `aud` | **未设置** | 单服务、单受众，`aud` 无区分意义；将来若拆分为"API 服务 + 批处理服务"再加（届时必须校验） |
| Payload | `sub` | `user.id`（字符串） | **只用内部 ID，不放用户名** |
| Payload | `role` | `student`/`admin`/`auditor` | 授权快速判定；服务端仍以 DB 为准做二次校验（角色变更后旧 token 里的 role 会过期） |
| Payload | **`ver`** | 整数，取自 `users.token_version` | **唯一的撤销机制**：与 DB 当前值不等即拒绝（见 §2.4）。注意 claim 名是 `ver`（数据库列名才是 `token_version`） |
| Payload | `jti` | `uuid4().hex` | 仅用于审计关联（把 token 与审计行串起来），**不参与撤销判定** |
| Payload | `iat` / `nbf` | 签发时间 / 生效时间 | `nbf = iat`，容忍时钟偏移 30s |
| Payload | `exp` | `now + 120 分钟` | 见 §2.3 |

**claims 收敛结果（已整改）**

最终 claims 集合固定为 **8 个**：`sub / role / ver / iat / nbf / exp / jti / iss`。

- `username` 已从 claims 移除（原实现写入）。理由：① 与本方案"claims 只放 `sub`/`role`/`ver` 三个身份要素"一致；② **用户改名后旧 token 里的用户名会过期**，属无收益冗余；③ 展示用名一律从 DB 查，多一次查询远比"令牌里躺着可能过期的身份信息"可控。
- 判断"某个字段能不能进 claims"只需一句：**这个值会不会随用户状态变化？** 会变的（用户名、角色以外的属性、口令版本以外的状态）一律不进，因为它一旦写进令牌就冻结到过期为止。

**禁止放进 claims**：邮箱、学号、口令哈希、API Key、对话内容、诊断结论。JWT 是 Base64 明文可读，等于公开。

**密钥管理**

| 项 | 要求 | 优先级 |
|---|---|---|
| `JWT_SECRET` 生成 | `python -c "import secrets;print(secrets.token_urlsafe(48))"`（≥32 字节熵）；v4 由 `config.resolve_secret_key()` 生成并落到 `data/.secret`（已 gitignore） | 【必做】 |
| 存放 | 仅 `.env` 或 `data/.secret`，不入库、不入仓、不进镜像 | 【必做】 |
| 轮换 | 泄露即换；正常情况毕设期内不轮换（配合 `kid` 可平滑） | 【建议】 |
| 缺失行为 | 启动失败（fail-fast），**禁止**代码里写默认 secret | 【必做】 |

> 注意：`data/.secret` 一旦删除，所有已签发 token 立即失效（等价于全员重新登录）。这不算故障，但需在运维说明里写清楚，避免"删了就删了"导致答辩现场全员掉线。

### 2.3 有效期与续期策略（单 access token）

| 项 | 取值 | 说明 |
|---|---|---|
| 令牌类型 | **仅 access token（无 refresh token）** | 部署形态：Streamlit 服务端代理，token 只存在于 `st.session_state` |
| TTL | **2 小时** | 由"用户体验"与"泄露窗口"共同决定：太短会频繁掉线（Streamlit 每次 rerun 都校验），太长会放大失窃窗口 |
| 存储位置 | **服务端 `st.session_state`**（进程内存） | 浏览器不持有 JWT：不落 `localStorage`、不落 Cookie、不出现在 URL |
| 撤销机制 | `users.token_version` 自增 | 与 claims 中的 `token_version` 比对，不等即 401（见 §2.4） |
| 时钟偏移容忍 | `leeway=30s` | 防本机时间漂移误判 |
| 过期行为 | 返回 401 → 前端跳登录页，提示"登录已过期，请重新登录" | 不做静默续期以外的任何自动处理 |

**为什么不设 refresh token（这段是答辩时的标准回答，别临场编）**

| 考虑 | 分析 |
|---|---|
| 前提 | refresh token 的存在意义是"**浏览器持有短期凭证、避免反复输密码**"。v4 的浏览器**根本不持有任何令牌**——请求由 Streamlit 服务端代理发出，令牌在服务端内存里。没有"前端要令牌"的场景，refresh 就没有存在理由，加了只是凭空多一个可被窃取的凭证 |
| 复杂度收益比 | refresh 要配套：`refresh_tokens` 表、rotation、重放检测、family 撤销、`sha256` 存储、7 天 TTL……约 1.5 人日，换来的只是"2 小时内不用重新输密码" |
| 撤销能力 | `token_version` 已覆盖改密、封禁、强制下线三个真实场景（**全局失效**）；refresh 唯一的额外能力是"撤销单个设备"，而本系统是个人用/校内小规模，无此需求 |
| 结论 | **不设 refresh，"2 小时 + `token_version`" 是这个部署形态下的正解** |

**可选增强（不是第二套方案，别在论文里写成并列方案）**

> 【建议】滑动续期：每次请求校验通过后，若 `exp - now < 15 分钟`，服务端静默重签一枚新 token 写回 `st.session_state`，用户无感知。这是**纯服务端动作**，不引入任何新凭证类型、不改变 §2.4 的撤销模型。做不做都不影响安全结论，只影响"会不会在演示中途被踢下线"——**答辩前建议做，成本约 20 行**。

### 2.4 登出与撤销模型

| 动作 | 服务端行为 | 生效范围 | 延迟 |
|---|---|---|---|
| 登出（主动） | 清空 `st.session_state` 中的 token 与用户信息 + 写 `AUTH_LOGOUT` 审计 | 本会话 | 立即（浏览器侧无凭证可残留） |
| 改密 | `token_version += 1` + 写 `AUTH_PASSWORD_CHANGE` | 该用户**全部会话** | 下次请求即失效 |
| 封禁/停用 | `status='disabled'` + `token_version += 1` + 写 `ADMIN_DISABLE_USER` | 该用户全部会话 | 下次请求即失效 |
| 密码重置/疑似泄露 | 同上（自增即可） | 该用户全部会话 | 下次请求即失效 |
| 密钥轮换（`data/.secret` 重建） | 所有 token 签名不再通过 | **全站** | 立即 |

**取舍说明（为什么不做 jti 黑名单）**

| 方案 | 撤销精度 | 成本 | 采纳 |
|---|---|---|---|
| `token_version` 版本号比对 | 用户级（全局失效该用户所有会话） | 每请求比对一个整数（随用户行一起读，可缓存 60s） | **采用（唯一机制）** |
| `jti` 黑名单表 | 单 token 级 | 要建表、每次撤销写一行、定期清理、每请求查一次 | 不采用：本系统无"只踢掉某一个设备"的需求，收益不足以抵消复杂度 |
| refresh + rotation | 单 token 级 | 1.5 人日 + 一套新凭证 | 不采用（见 §2.3 理由） |

**这个选择的已知局限，必须在论文里主动写出来（写出来是加分，被问出来是扣分）**

| 局限 | 补偿控制 |
|---|---|
| 单个 token 被盗时最长有 **2 小时**窗口无法单独撤销（只能让该用户所有会话一起失效） | ① token 不出服务端，窃取前提是已能读服务端内存（此时已全面失守）；② 2 小时窗口有限；③ 一旦发现异常，`token_version += 1` 立即全失效；④ 登录/改密/越权全部留审计，可追溯 |
| 强制重新登录会打断正在进行的操作 | 滑动续期（§2.3 可选增强）；答辩前把 TTL 临时调大并说明原因 |
| Streamlit 自身会话也会过期 | 与 JWT TTL 对齐；页面空闲超时提示"会话已过期，请重新登录"而不是静默失败 |

> **另一个必须知道的技术事实**：这个形态下浏览器持有的是 **Streamlit 会话本身**（会话 id 关联着服务端 `session_state`），不是 JWT。所以"浏览器不持有令牌"降低了凭证泄露面，但并不等于零风险——剩余风险是**会话劫持**（拿到 session id 即可操作该会话）。对应控制：① 必须 TLS（或严格限定 `localhost`）；② 限制同一账号并发会话数（【建议】）；③ Streamlit 会话闲置超时与 JWT TTL 对齐。答辩被问"浏览器端到底存了什么"时，答"只有会话 id，没有任何 bearer token"，比含糊说"前端不存东西"稳。

### 2.5 登录失败限流与账号锁定

| 维度 | 阈值 | 处置 | 记录事件 |
|---|---|---|---|
| 单账号（username） | 5 分钟内失败 ≥ 5 次 | 锁定 15 分钟，返回统一提示"登录失败次数过多，请稍后再试" | `AUTH_LOCKED`（WARN） |
| 单 IP | 10 分钟内失败 ≥ 20 次 | HTTP 429 + 指数退避（Retry-After 60s 起，翻倍，上限 15 min） | `AUTH_LOGIN_FAIL`（WARN） |
| 全站 | 1 分钟内登录尝试 > 100 | 记日志 + 控制台告警（毕设不自动封站） | `AUTH_RATE_ALERT`（ERROR） |
| 成功登录 | — | 清零该账号失败计数 | `AUTH_LOGIN_SUCCESS` |

**防用户名枚举**：无论用户是否存在，都执行一次哈希运算（用户不存在时对一个固定的 dummy hash 校验），响应时间与文案完全一致。

```sql
CREATE TABLE login_attempt (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  username   TEXT NOT NULL,
  ip         TEXT NOT NULL,
  success    INTEGER NOT NULL DEFAULT 0,
  ua         TEXT,
  created_at TEXT DEFAULT (datetime('now'))
);
CREATE INDEX idx_att_user_time ON login_attempt(username, created_at);
CREATE INDEX idx_att_ip_time   ON login_attempt(ip, created_at);
```

> **限流状态存哪里：按部署形态决定，不要一概而论**
> - **单进程部署**（当前形态：Streamlit 单实例）→ 进程内滑动窗口（`LoginThrottle`）**可以接受**，实现最简；代价是**进程重启后计数清零**，需在运维说明里写明（对毕设场景无实质影响）。
> - **多 worker / 多实例部署** → 进程内计数会被绕过（打不同 worker 各计各的），**必须**改存 DB（`login_attempt` 表）或共享存储。
> - 因此本项优先级为：单进程【已达标】；多 worker【必做】。答辩被问"重启能不能绕过限流"时，如实答"能，但单进程部署下重启意味着服务中断，攻击者无法用重启获益"，这比含糊过去好。

### 2.6 v3 → v4 迁移要点

| 项 | 处置 | 优先级 |
|---|---|---|
| 旧 `users` 表 | 保留 `username / password_hash / role / create_time`，新增 `token_version INTEGER DEFAULT 0`、`must_change_password INTEGER DEFAULT 0`、`status TEXT DEFAULT 'active'`（与当前 `models.User` 一致） | 【必做】 |
| 旧 PBKDF2 哈希（20 万次） | 直接兼容校验，登录成功后自动 rehash 到 60 万次 | 【必做】 |
| role 取值 | 由 `student/admin` 扩展为 `student/admin/auditor`，DB 加 CHECK 约束 | 【必做】 |
| `admin` 默认账号 | 启动脚本生成随机初始口令并打印一次（或强制首次改密），**不再写死默认值** | 【必做】 |
| Streamlit `st.session_state` 登录态 | 由 JWT 承载，但仍存于服务端 `st.session_state`（浏览器不持有）；每次请求校验签名 + `exp` + `token_version` | 【必做】 |

## 3. RBAC 权限矩阵

### 3.1 角色定义与职责分离

| 角色 | 定位 | 核心权限 | 明确禁止（职责分离） |
|---|---|---|---|
| `student` | 学生（默认角色） | 本人会话/消息/诊断/统计的读写；知识库**已发布**内容只读；导出本人数据 | 不能看他人任何数据；不能写知识库；不能看全站统计；不能导出全库 |
| `admin` | 管理员/助教 | 知识库 CRUD 与导入；用户管理（不含改自己角色）；全站统计；运营任务 | **不能删除/修改审计日志**（只读最近 7 天）；默认**不能读他人对话原文**（只能看元数据） |

### 3.4 数据级（ABAC）约束

角色只决定"能不能调这个接口"，行级约束决定"能看哪几行"。v4 统一规则：

| 规则 ID | 适用资源 | 约束表达式 | 实现位置 |
|---|---|---|---|
| R1 | session / message / diagnosis / submission | `resource.user_id == token.sub` | 仓储层强约束，**SQL 里带 `AND user_id=?`，不做"先查后判"** |
| R2 | knowledge | `status == 'published'` 才对 `student` 可见；`draft/reviewing/retired` 仅 `admin` | 查询条件拼装（非过滤器后置） |
| R3 | knowledge | `visibility != 'restricted'` 才对 `student` 返回；`restricted` 仅 `admin` 可见且访问写审计 | 同上 |
| R4 | audit | 表级 append-only：`UPDATE`/`DELETE` 由触发器 `RAISE(ABORT)` | DB 触发器 |
| R5 | 导出 | 单次导出上限 5000 条；同一用户 24h 内 ≤ 3 次；导出文件含"用户名+时间"水印 | 服务层 + 审计 |
| R6 | 检索/生成 + 知识读取 | **与实现一致的三条件**（缺一即不放行）：`is_deleted = 0` **且** `status = 'published'` **且** `visibility != 'restricted'`。必须作用于**三个出口**：① RAG 候选入口（已实现 fail-closed）② `GET /knowledge` 列表 ③ `GET /knowledge/{id}` 详情（含 `similar`）。**`sensitivity` 不作为召回开关**（原因见 §6.8），但决定脱敏规则与导出权限；【建议】追加兜底 `sensitivity != 'L4'` | 检索层 + 知识 API 层（两处都要，只做一处等于没做） |

> **R6 为什么写成三个条件而不是只写 `sensitivity IN ('L1','L2')`**：当前语料 100% 为 L2/internal（见 02 文档盘点结论），白名单条件在**今天**足够；但白名单是"当前数据分布"的函数，不是规则本身。将来一旦引入校内独家题解、内部评测数据、教师私有笔记（`visibility='restricted'`），只靠 sensitivity 白名单会**默认放行**。多一个 `AND` 条件的成本是 0，省掉的是将来的返工与一次内容外发事故。论文里也应表述为"按最小必要做三重过滤"，而不是"因为当前没有受限内容所以不用过滤"——后者在答辩追问"以后有了怎么办"时无法回答。

**字段名以 02 文档为唯一准（本文档引用须一致）**

| 字段 | 取值（精确拼写） | 备注 |
|---|---|---|
| `sensitivity` | `L1` / `L2` / `L3` / `L4` | 大写 L + 数字，不写 public/internal |
| `visibility` | `public` / `internal` / `restricted` | 全小写；只能由 `sensitivity` 收紧，不可放宽 |
| `owner_type` | `platform` / `external` / `user` | 权利来源，非加工方 |
| `content_origin` | `metadata` / `self_written` | 分开计数，不得合并成一个"知识条目数" |
| `retention_days` | 整数；`0`=永久（仅 L1/L2）；L3=`180`；审计=`180` | |
| 来源链接 | **`origin_url`** | 统一命名，不用 `source_url` |
| 许可 | **`license`**：`CC-BY-NC-SA-4.0` / `internal-only` / `Codeforces-Terms` / `AtCoder-Terms` | |

### 3.5 越权防护要点

| 风险 | 防护 | 优先级 |
|---|---|---|
| IDOR（改 URL 里的 id 看别人数据） | 每个 `/{id}` 端点强制 owner 校验；**禁止** `get_by_id()` 后再在 Python 里判断（易漏） | 【必做】 |
| 水平越权测试 | 测试用例至少 3 条：学生 A 读 B 的会话、学生 A 删 B 的诊断、学生改自己 role | 【必做】 |
| 垂直越权 | `role` 从 **DB 读**，不完全信任 JWT 里的 role（角色变更后旧 token 仍带旧 role） | 【必做】 |
| 越权尝试留痕 | 一律返回 403 且写 `access_denied` 审计。**实现方式**：在 `Forbidden` 异常处理器统一落库（带 `trace_id`），**不要**在每个路由手写——依赖层拿不到 `request`，手写必然漏记，而"漏记的那次"恰恰可能是攻击者试探的那次 | ✅ 已实现（异常处理器） |
| 批量导出扩散 | 导出限流 + 条数上限 + 水印；导出行为单独审计 | 【必做】 |
| CORS | 白名单精确到源（`http://localhost:5173`），禁止 `*` 与 `allow_credentials` 同用 | 【必做】 |
| HTTP 方法 | 状态变更只允许 POST/PATCH/DELETE；GET 无副作用 | 【建议】 |
| 错误信息 | 生产环境不返回堆栈；统一 `{"code":"...","message":"..."}` | 【必做】 |
| **响应字段白名单** | 用户对象只出 `id/username/role/created_at`；**禁止**回传 `password_hash`、`token_version`、`is_active`、`last_login_at`、`failed_count` 等内部状态字段。用独立的 `UserResponse` schema，**不要 `model_config = {"from_attributes": True}` 直接把 ORM 对象丢出去**——那会把整行字段全暴露 | ✅ 已实现（`UserResponse`） |

> 注意：加了 DELETE 触发器后，**任何"清理旧审计"的脚本都会失败**——这正是设计意图（审计只增不减）。若将来要做归档，走"导出后整库归档"而不是 DELETE。

### 4.3 留存期与归档

| 数据 | 留存期 | 依据 | 到期动作 |
|---|---|---|---|
| 审计日志 | **≥ 180 天**（毕设环境可实现 90 天 + 归档，答辩时说明"设计值为 6 个月"） | 网络安全法第 21 条、等保 2.0 三级"审计记录留存不少于 6 个月" | 归档为 `audit_YYYYMM.csv.gz`（只读、校验哈希） |
| 登录尝试记录 | 90 天 | 最小必要 | 自动清理 |
| 用户对话 | 180 天，或用户删除即删 | PIPL 最小必要 + 删除权 | 硬删 + `VACUUM` |
| 诊断记录 | 180 天 | 同上 | 同上 |
| 检索/生成 trace（非审计部分，明细日志） | 30 天 | 排障需要 | 滚动删除 |
| 应用日志 `logs/app.log` | 7 天（2MB × 3 滚动） | 排障 | 自动滚动 |

> PIPL 删除权与审计留存冲突的处理：用户要求删除对话时，**删除消息内容**，但保留一条 `EXPORT_DATA`/`DATA_DELETE` 类审计**元数据**（谁在何时删了哪个 id，不含内容）。这样既满足删除权，又保留可追责的操作痕迹。

### 4.4 审计脱敏规则（**最容易出错的地方**）

| 内容 | 允许入审计？ | 正确做法 | 优先级 |
|---|---|---|---|
| 用户口令（明文或哈希） | **绝对禁止** | 只记 `reason=bad_password`，不记任何输入值 | 【必做】 |
| JWT token | **绝对禁止** | 只记 `jti`（uuid）与 `token_version`；如需关联，记 token 的 `sha256` 前 8 位 | 【必做】 |
| API Key | **绝对禁止** | 只记 `value_fingerprint = sha256(key)[:8]` | 【必做】 |
| 学生提问原文 | **默认不记**（审计表） | 审计记 `question_hash`（sha256 前 16）+ `question_len`，必要时记前 20 字符（可配置，默认关） | 【必做】 |
| 检索 query 原文 | **可记，但仅限 `retrieval_logs` 且受三条件约束** | 见下"★ retrieval_logs 的合规约束" | 【必做】 |
| 检索命中的知识正文 | 不记 | 只记 `hit_ids` 与 `best_distance` | 【必做】 |
| 代码片段（诊断） | 不记全文 | 记 `code_hash` + 行数 + 语言 | 【必做】 |
| 学生姓名/学号/邮箱 | 不入审计 | 审计只用 `user_id` | 【必做】 |
| IP | 记（安全必需，属最小必要） | 查询展示按角色：`auditor` 看全量，`admin` 看 `a.b.c.*` | 【建议】 |
| 错误堆栈 | 不入审计 | 入应用日志（同样过滤 `Authorization`/`sk-`） | 【必做】 |

**日志统一过滤器（v3 `logger.py` 的 v4 升级）**：给 `logging.Filter` 加正则，命中 `sk-[A-Za-z0-9]{16,}`、`Bearer\s+\S+`、`password\s*[=:]\s*\S+`、`\d{11}`（手机号）、`\d{17}[\dXx]`（身份证）的片段替换为 `***`。这层是"兜底防线"，不能替代写入前脱敏。

**★ `retrieval_logs` 的合规约束（三条已全部落地）**

`models.py::RetrievalLog` 的 `query: String(255)` 用于调优命中率（有明确正当用途），但**不落原文**：落库前经 `fingerprint_query()` 指纹化为 `sha256 前 16 位 + 原文长度`（如 `sha256:ab3b50ce74f0d2e8#len=21`），既能区分不同查询（排障时对比两次请求是否同文），又不可逆推出原文。它不在审计表里，属 L3 明细日志，因此不违反"审计不记原文"的规则，但必须配套三条——否则就是一个"审计很干净、旁边另有一张表存着原文"的假合规：

| 约束 | 做法 | 状态 |
|---|---|---|
| ① 写入前脱敏 | `query` 落库前经 `fingerprint_query()` 指纹化（`sha256 前 16 位 + 原文长度`，`security.py`），**连原文都不落库**，强于原"正则替换"方案——学生把个人信息粘进提问也不会被明文留存 | ✅ 已落地 |
| ② 与删除权联动 | 新增 `purge_user_logs(user_id)`，用户删除会话/撤回同意时同步清理其明细日志（原来的 `purge_retrieval_logs(keep_days)` 只按时间清理，覆盖不到删除权） | ✅ 已落地 |
| ③ 不对外导出 | `/api/export/my-data` 与审计导出均**不含** `retrieval_logs`（它是系统调优数据，不是"用户的个人数据副本"） | ✅ 原有设计已满足 |

> 一句话原则：**明细日志的最好状态是"不存原文只存指纹"**；即使不得不存原文，也必须"能删、能脱敏、不外流"。这三条缺任一条，L3 数据的处理就站不住。

**另一处必须自己先说清的边界（否则会被当成漏洞）**：`GET /knowledge/{id}` 返回的 `content` **不是完整题面**，而是"自写正文"或"元数据加工摘要"（`entry_type` 为 `solution`/`concept`/`strategy`/`hint`）。所以**不存在"通过 API 合法获得题面全文"这条链**——这是设计使然，不是遗漏。答辩时主动说这一句，比等评委追问"你们接口是不是能拿到题面"要好；同时它也是 §6.7 长度门禁（元数据类 ≤500）存在的意义：**保证这条边界不被数据慢慢撑破**。

### 4.5 告警阈值

| 告警项 | 阈值 | 级别 | 处置 |
|---|---|---|---|
| 单账号登录失败 | 5 分钟 ≥ 5 次 | WARN | 自动锁定 + 控制台提示 |
| 单 IP 认证失败（401/403） | 1 小时 ≥ 30 次 | WARN | 429 限流 |
| 越权尝试 `ACCESS_DENIED` | 单账号 1 小时 ≥ 10 次 | **HIGH** | 通知 admin，考虑临时封号 |
| 数据导出 | 单人 24h ≥ 3 次 或 单次 > 5000 行 | **HIGH** | 阻断 + 人工确认 |
| LLM token 消耗 | 单日 > 设定上限（如 200 万 token） | **HIGH** | 熔断当日生成，排查 Key 盗用 |
| 失效 token 仍被使用 | 任意一次（`token_version` 不匹配却持续重试） | **HIGH** | 判定为"用旧凭证试探"，记 `ACCESS_DENIED` + 溯源 IP；同账号 10 分钟内 ≥3 次则临时封号 |
| 审计写入失败 | 任意一次 | **CRITICAL** | 主流程返回 503（fail-closed），禁止"无审计继续跑" |
| 爬虫 4xx/5xx | 连续 5 次 | WARN | 熔断该站点 30 分钟 |

## 5. 数据安全分级

### 5.1 分级矩阵

| 级别 | 定义 | 示例数据 | 存储要求 | 传输要求 | 访问控制 | 脱敏要求 |
|---|---|---|---|---|---|---|
| **L1 公开** | 可对外展示，泄露无损害 | 题目标识（题号/标题）、标签、难度、rating、公开统计数字、来源 URL | 明文 | 无特殊 | 登录即可读（甚至匿名可读） | 无 |
| **L2 内部** | 仅系统内使用，泄露影响有限 | 自写题解正文、爬取元数据、知识点映射表、检索参数阈值、prompt 模板 | 明文，随 DB 备份 | 内网 | 登录用户只读；写需 `admin` | 导出/论文引用时保留来源署名 |
| **L3 受限** | 含个人信息或可识别学习行为 | 用户对话内容、代码片段与诊断记录、练习/提交记录、用户名、邮箱、IP | 库文件加密或磁盘加密；备份加密 | TLS（或明确标注仅 localhost） | 仅本人 + 有限元数据给 `admin`/`auditor` | 对外导出假名化（`U001`） |
| **L4 机密** | 泄露即造成直接损失 | 口令哈希与盐、`JWT_SECRET`、`DEEPSEEK_API_KEY`、审计日志原文、DB/备份文件 | 仅 `.env`（权限 600）+ 独立备份目录；**不入库**（口令哈希等字段除外，见下） | 仅本机读取 | 无 API 可达（**指字段/文件层，见下方双层表述**）；运维手工 | 日志只记指纹 |

#### 5.1.1 L4 的"无 API 可达"要分两层说（重要，否则自相矛盾）

L4 的控制目标不是"这一行数据永不被进程读取"（那系统就无法运行），而是"**任何 API 都不能把 L4 值原样返回给调用方**"。因此必须分两层表述，两处引用时口径一致：

| 层 | 对象 | 级别 | 管控要求 |
|---|---|---|---|
| **静态文件层** | `acm_system.db` 文件本体、`backup/` 备份、交付用 `.zip` 包 | **L4（整文件取最高项）** | 不对任何接口暴露；不入 git、不随作业包外发、不放共享盘/网盘；备份加密；仅运维手工访问 |
| **运行期访问层** | 进程内经数据层读写的**具体表/列** | **按表分级** | `users.password_hash` 列 = L4（永不出接口）；对话/代码/诊断/练习表 = L3（仅本人，经 API 读写）；知识元数据表 = L2；接口一律返回字段白名单 |

这样既保住"任何人不得以'这是本地文件'为由给 DB 降级"的原意（文件层仍是 L4），又不会写出"L4 无 API 可达"却在代码里天天读写该库的矛盾表述。

> 反例（论文里千万别这么写）：把整库标 L4 并声明"无 API 可达"，同一篇又描述"会话记录通过 API 实时读写"——评委一眼就能看出两句话互斥。正确写法是上面那张两层表。

### 5.2 逐项落地

| 数据项 | 级别 | 表/位置 | 留存 | 关键控制 |
|---|---|---|---|---|
| 题号、标题、标签、难度、rating、来源 URL | L1 | `knowledge`(元数据列) | 永久（可随时重抓） | 只存元数据不存题面正文（见 §6.5） |
| 自写题解/教学讲解 | L2 | `knowledge.content` | 永久 | 入库审核后才 `published`；`source` 保留出处 |
| 知识点/错因词表 | L2 | `diagnosis/knowledge.py` | 随版本 | 版本化，改动走审核 |
| 用户对话 | L3 | `chat_history` | 180 天 | owner 校验；送入 LLM 前脱敏；审计不记原文 |
| 诊断记录（含代码片段） | L3 | `diag_diagnoses` | 180 天 | 同上；用户可删 |
| 练习/掌握记录 | L3 | `submissions` / `diag_user_skills` | 180 天 | 导出仅本人 |
| 用户名 | L3（弱标识） | `users.username` | 账号存续期 | 审计只记 `user_id` |
| 口令哈希 + 盐 | L4 | `users.password_hash` | 账号存续期 | PBKDF2 60 万次；任何接口不返回 |
| `JWT_SECRET` | L4 | `.env` | 长期 | 不入库不入仓；泄露即轮换 |
| `DEEPSEEK_API_KEY` | L4 | `.env` | 长期 | 同上；日志只记指纹 |
| 审计日志 | L4 | `audit_logs` | 180 天 | 应用层 append-only（无 update/delete 入口）+ 建议加 DB 触发器；导出受限 |
| DB 文件 / 备份（**静态文件层**） | L4 | `*.db`、`backup/`、交付 `.zip` | 按备份策略 | 加密（至少 zip 加密）；不放共享盘/网盘；不随作业包外发 |
| 检索/生成明细日志 | L3 | `retrieval_logs` / `logs/trace.jsonl` | 30 天 | 统一脱敏过滤器；`query` 落库前指纹化（`fingerprint_query`，不落原文）；与删除权联动（`purge_user_logs`）；不对外导出（§4.4） |
| 审计日志容量 | L4 | `audit_logs` | 180 天 | 按**事件数**估算：日活 20 人 × 3 次提问 ≈ 200 行/天 × 300 B ≈ 60 KB/天 → 180 天约 **11 MB**（若 `RETRIEVE`/`GENERATE` 落 jsonl 不入库，降至约 **4 MB**）。SQLite 完全无压力 |

> 【必做】`*.db` 必须在 `.gitignore` 中（v3 已忽略），且**不得**打进交作业的压缩包。
> 【必做】口径统一：v3 的 `acm_system.db` **文件本体按 L4 计**（含全部口令哈希与对话，取最高项），但**运行期按表分级**（口令哈希列 L4 / 对话诊断表 L3 / 知识表 L2）。任何材料都不得简化成"整库 L4 且无 API 可达"——那与系统实现互斥，详见 §5.1.1。

### 5.5 送 LLM 的数据边界（**必须实现的一道闸**）

| 检查项 | 规则 | 实现位置 |
|---|---|---|
| 只发最小上下文 | 当期问题 + top-k 检索片段（≤6 条）+ 近 3 轮历史 | `chat_service` 组装 prompt 处 |
| 不传身份标识 | prompt 中不含 username / user_id / 会话标题里的姓名 | 同上，用模板变量白名单 |
| 发送前脱敏 | 正则过滤 `sk-`、`password=`、手机号、身份证、邮箱 → 占位符 | 统一 `sanitize_before_llm()` |
| 机密知识不外发 | `visibility='restricted'` 的知识条目不得进入检索结果（R6） | 检索层过滤 |
| 不记录完整 prompt | 日志只记模板版本 + token 数 + trace_id | `GENERATE` 审计 |

## 6. 爬虫合规

### 6.1 目标站点与接入方式（先选"合法省事"的通道）

| 站点 / 资源 | 用途 | **推荐接入方式** | 频率约束 | 备注 |
|---|---|---|---|---|
| `codeforces.com/api/*` | 题目列表、用户提交、比赛列表 | **官方 API（首选）** | 官方文档：**每秒最多 1 次请求**，超出返回 429；必须遵守 | 有稳定 JSON schema，无需解析 HTML |
| `codeforces.com/problemset/*` | 题面/标签页面 | **不抓页面**（用 API 的 `problemset.problems` 已含题号、名称、标签、rating） | — | 只有当 API 缺字段（如需题面摘要）才考虑，且限速 ≤ 1 QPS |
| `kenkoooo.com/atcoder/resources/*.json` | AtCoder 题目元数据、难度、AC 数 | **下载静态 JSON 数据集（首选）** | 单次下载，每日最多 1 次 | 由 AtCoder Problems 项目公开提供，**务必先读其 README 与使用条款并署名** |
| `atcoder.jp` | 题面页面 | **不抓**（用上面的 JSON 数据集替代） | — | 抓页面属高风险，非必要不碰 |
| 洛谷 / OI Wiki 等 | 教学讲解 | **人工少量摘录并改写 + 署名链接**，不批量抓 | — | 版权边界：只链不抄 |

> **原则**：能拿到结构化 API / 公开数据集，就绝不写 HTML 爬虫。这既是合规要求，也让"知识加工流水线"更稳定（少了 HTML 解析的维护成本）。

### 6.2 请求规范

| 项 | 规则 | 优先级 |
|---|---|---|
| User-Agent | `ACM-RAG-Practice/0.1 (graduation project; contact: <学校邮箱>)` — **必须能联系到人**，禁止伪装成浏览器 UA，禁止空 UA | 【必做】 |
| QPS | Codeforces API ≤ **1 次/秒**；页面类（若确需）≤ **0.5 次/秒**；并发数 = 1 | 【必做】 |
| robots.txt | 启动前 `GET /robots.txt` 解析：`Disallow` 路径跳过；`Crawl-delay` 取 `max(robots值, 我们的间隔)`；robots 拉取失败则**保守跳过该站点** | 【必做】 |
| 抓取时间窗口 | 全量任务放 02:00–06:00；白天只做增量小任务 | 【建议】 |
| 超时与重试 | 超时 10s；重试 ≤ 3 次；指数退避 `2^n + jitter`（2s/4s/8s） | 【必做】 |
| 429 / 503 | 尊重 `Retry-After`，无该头则退避 60s 起；连续 3 次即熔断该站点 30 分钟 | 【必做】 |
| 403 / 401 | **立即停止该站点**并告警（可能已封禁），不反复试 | 【必做】 |
| 条件请求 | 支持 `ETag/If-None-Match`、`If-Modified-Since`，304 时不重复解析 | 【建议】 |
| 压缩 | 带 `Accept-Encoding: gzip`（礼貌且省流量） | 【建议】 |
| 日志 | 每次任务写 `CRAWL_RUN` 审计：站点、UA、请求数、状态码分布、耗时 | 【必做】 |

### 6.3 增量抓取策略

| 数据类型 | 策略 | 去重键 |
|---|---|---|
| 题目元数据（`problemset.problems`） | 全量拉取（约 10MB 级 JSON，可接受），本地 diff 出新增/改动 | `contestId + index`（如 `1900A`） |


### 6.5 版权边界（论文里必须写清楚的一段）

| 对象 | 是否落库 | 理由 |
|---|---|---|
| 题目标识（contestId/index）、标题、标签、官方难度、rating、来源 URL | ✅ 存 | 事实性元数据，不构成实质性表达 |

| 自写题解、讲解、错因分析 | ✅ 存 | 原创内容，标注作者与许可 |
| 公开统计（AC 数、通过率） | ✅ 存 | 聚合数据，标注数据来源 |

**关于 `fetched_at` 是否独立成列的结论：不独立成列，留在 `meta_json`。** 理由：

| 判断维度 | 结论 |
|---|---|
| 是否进 WHERE | 否——它只用于展示（"抓取于某日"）与审计回溯，不做范围查询 |
| 能否用 `created_at` 代替 | **不能**。`created_at` 是**入库时间**，`fetched_at` 是**抓取时间**；重跑导入、批量补录、从缓存重建时两者会差数小时到数天。用 `created_at` 冒充，等于在答"这批数据哪次抓的"时给出错误答案——**比不写更糟**，因为它看起来有值 |
| 落地要求 | `meta_json.fetched_at` **必须显式写入**（取请求响应时间或任务开始时间，ISO8601 UTC），不得留空、不得默认填 `created_at` |

**残余问题 3：长度门禁按类型分档 —— ✅ 已整改**

原状：`MAX_CONTENT_CHARS = 2400` 且不区分条目类型，正则拒收只有四条（`样例输入`/`样例输出`/`sample input`/`sample output`/`输入格式[:：]{80,}`/`输出格式[:：]{80,}`）。问题在于**2400 字符足够塞进一段完整题面**，而无标记的题面描述不会被正则拦住——"只存元数据不转载题面"最核心的那句表述会被击穿。

**已实施的分档（`quality_gate` type-aware）**：

| 条目形态 | 上限 | 理由 |
|---|---|---|
| `考点提示` / `题面摘要`（元数据加工类） | **≤500 字符** | 元数据摘要不该这么长；超长即高度疑似题面转载 |
| `题解` / `知识点卡` / `元知识`（自写类） | ≤2400 字符（维持） | 精讲需要容纳复杂度分析、易错点等内容 |
| **溯源字段**（只展示/审计，不参与查询） | `license`、`fetched_at`、`content_origin`/`entry_type`、`processed_by`、`mirror` | 统一放 `meta_json TEXT` 一列 | 减少 ALTER 次数与模型膨胀；门禁在**写入前**校验（不能"只存不管"） |

```python
# 建议加入 db/session.py::_ensure_columns 的 additions
"knowledge_items": {
    "status":         "TEXT DEFAULT 'published'",   # draft/reviewing/published/retired
    "visibility":     "TEXT DEFAULT 'internal'",    # public/internal/restricted
    "sensitivity":    "TEXT DEFAULT 'L2'",          # L1/L2/L3/L4
    "retention_days": "INTEGER DEFAULT 0",          # 0=永久（仅 L1/L2）
    "meta_json":      "TEXT",                       # license/fetched_at/entry_type/processed_by/mirror
},
```

**`source` 的语义（v1.9 仲裁后的定稿）**：`source` 是**检索分区键**（承重 `type_boost` / 精讲配额插入 / `eval --verify` 护栏），取值域 `{curated, cf, atcoder, manual}`——`cf`/`atcoder` 是站点缩写并承担"权利主体/删除响应找哪个平台"的语义，`curated`/`manual` 承担语料形态语义。~~原裁定"source = 来源站点 `codeforces`/`atcoder`/`manual`、`entry_type = curated`/`meta`"已被 v1.9 仲裁覆盖~~（默认值 `"manual"` 保留，它属于取值域）。**四件事不能合并**的原则不变，但承载位置改为：

| 字段 | 回答的问题 | 取值 / 落位 |
|---|---|---|
| `source` | 检索分区 + 站点缩写（删除响应找哪个平台） | `curated` / `cf` / `atcoder` / `manual`（**列**） |
| `meta_json.content_origin` | 谁写的（版权归属与责任） | `self_written` / `metadata` |
| `meta_json.owner_type` | 权利来源 | `user` / `platform` |
| `meta_json.license` | 受哪份条款约束 | `Codeforces-Terms` / `AtCoder-Terms` / `internal-only`（枚举含 `CC-BY-NC-SA-4.0`，本库未使用） |
| `mirror`（✅ **第 8 键已落地并复核销项**） | 经由哪个通道 / 镜像 | `kenkoooo`（AtCoder）/ `official-api`（CF）/ `n/a(self_written)` |

> 原则不变：**权利主体、通道、许可、谁写的**四件事不能合并。把 `source` 写成 `kenkoooo` 会让权利主体在库里消失；反过来只写 `atcoder` 不写 `mirror`，则"该停哪个通道"答不上来——两端都是溯源断链。

### 6.8 `restricted` 的隔离层级（已定死，三个出口均已闭环）

**结论：`restricted` 照常入向量库，隔离发生在"取回之前"而非"存储"，且必须覆盖三个出口。**

| 方案 | 后果 | 采纳 |
|---|---|---|
| A. restricted 干脆不入向量库 | 连 `admin` 也无法用 RAG 检索内部独家资料；将来恢复要重建索引 | ✘ |
| B. 入向量库，在**候选入口**过滤（fail-closed） | 受限条目连候选池都进不去，日志/trace/`sources`/prompt 四处自然不含它 | **✔ 已实现** |
| C. 先取回再剔除 | **泄露在"取回"那一刻已经发生**（可能进日志、进 trace、进调试面板） | ✘ |

**三条件（与代码实现一致，缺一即不放行）**：`is_deleted = 0` **且** `status = 'published'` **且** `visibility != 'restricted'`。

> `is_deleted` 这一条是 02 文档追问时补上的：`knowledge_items` 是**软删**表（`is_deleted` 标记），此前条件里没有它，导致**已删除的条目仍会被检索命中**。软删是"用户以为删了、系统还留着"的常见陷阱，凡是有 `is_deleted` 的表，所有读路径都必须显式带上它。

**`sensitivity` 为什么不作为召回开关（这一点团队有过分歧，定稿如下）**

| 观点 | 结论 |
|---|---|
| 主张 `sensitivity IN ('L1','L2')` | 精讲类条目默认就是 `L2`，把它当召回开关**对精讲无副作用**，但一旦有人把精讲标成 `L3`（例如含内部评测数据），整条精讲会静默消失——**用密级控制"能不能看"，不该用来控制"能不能被检索"** |
| 主张只看 `status + visibility` | 职责更清晰：`visibility` 决定可见范围，`status` 决定发布状态；`sensitivity` 决定**脱敏规则与导出权限** |
| **定稿** | **`sensitivity` 不作召回开关**（以实现为准），但【建议】追加一行兜底 `sensitivity != 'L4'` |

**为什么仍建议加 `sensitivity != 'L4'` 这一行**：它不是"密级当召回开关"，而是**防填错**。`visibility` 是人工/加工侧写入的字段，一旦某条机密条目误填 `visibility='internal'`，仅有 `visibility != 'restricted'` 就拦不住；而 `sensitivity='L4'` 是机密级的强标识，用它兜底可以把"填错一个字段就泄露"降级为"填错两个字段才泄露"。**成本 1 行，收益是给人工错误留一道冗余。** 注意它只挡 L4，不影响 L1/L2/L3 的召回（精讲默认 L2，完全不受影响）。

**三个出口，逐一核对**

| # | 出口 | 规则 | 状态 |
|---|---|---|---|
| ① | **RAG 候选入口**（BM25 + 向量两路召回） | 逐条 `_visible(doc)` 判断后跳过 | ✅ 已实现（fail-closed） |
| ② | **`GET /knowledge` 列表** | SQL 里带 `status`/`visibility` 条件 | ✅ 已实现：`KnowledgeRepository.search()` 已加 `status='published'` + `visibility != 'restricted'` 过滤（`include_restricted` 仅 admin 可用） |
| ③ | **`GET /knowledge/{id}` 详情**（含 `similar` 相似推荐） | 同上，且非 admin 访问 `restricted` 返回 404（不返回 403，避免泄露"存在性"） | ✅ 已实现：`get_visible()` 详情专用，越权访问返回 **404** |

**为什么②③必须单独实现（此段保留作设计教训）**：候选入口过滤只能保护"检索这条路径"。但知识库有独立的列表与详情接口，学生只要拿到（或猜到）一个 id，就能绕过检索直接读取。这是最典型的"补了一个入口、漏了另一个入口"——**三条件的意义在于它是同一组规则，必须出现在每一条读路径上**，不能只出现在看起来最危险的那条。

**另加两条**：
- `admin` 访问 `restricted` 条目时写审计（`KB_READ_RESTRICTED`，WARN）——敏感内容每次访问都要留痕；
- 单元测试：构造一条 `restricted` + 一条 `is_deleted` 条目，断言它们**既不在检索结果中、不在 prompt 中、也不在列表/详情接口返回里**。四个断言都过，才算真的隔离。
