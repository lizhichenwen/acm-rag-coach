## 一、题目定位（问题域—技术域—价值域）

### 1.1 一句话版本（答辩开场用）

> 本系统面向 ACM 程序设计竞赛训练场景，构建一个**以检索为证据源、以"引导不代写"为行为约束**的 RAG 智能陪练系统：在 8,558 条经治理的竞赛知识上实现 BM25 与向量的混合检索与重排，将检索结果作为强制证据约束大模型输出，并结合 15 维静态代码特征完成错因诊断与能力画像闭环；相较直接调用通用大模型，本系统在检索命中率、代写率、错因定位准确率上给出可复现的量化改进，并以 FastAPI 分层后端、RBAC 与可观测性达到可部署的工程标准。

### 1.2 三段式拆解

| 维度 | 表述 | 支撑要点 |
|---|---|---|
| **问题域** | 竞赛训练中的"知识供给"与"错误归因"双缺口：题解知识高度碎片化（博客/OI Wiki/官方 editorial 混杂、中英混排、同一题多种解法），选手在"卡题—看题解—下次仍不会"的循环里失效；现有 OJ 只返回 AC/WA/TLE 判定而不给错因；通用大模型倾向直接输出完整代码，形成"代写"，破坏训练价值。 | v3 已有 67 题解 + 10 条竞赛元知识、意图识别中的"索要代码"类、诊断模块 15 类错因编码（ET01–ET15）——问题域来自真实使用反馈，非虚构场景。 |
| **技术域** | RAG 在垂直小语料上的四个硬约束：①**长尾召回**——短查询（"这题为什么 TLE"）对长文档，稠密检索偏向语义泛化、丢失标识符与复杂度关键词；②**证据约束**——生成端必须"有据可依"，需要引用与拒答机制而非纯 prompt 提示；③**多轮对齐**——追问 3 轮后查询漂移，需查询改写与会话级检索策略；④**规模化治理**——数据从 77 条到 8,558 条时，去重、标签归一、数据契约成为主要工程量。 | 对应 v4 的混合检索 + RRF、cross-encoder 重排、意图路由 + 引用约束、查询改写、爬虫与清洗流水线五项技术动作。 |
| **价值域** | 交付可度量、可复现、可部署的三件套：**准确性**（Hit@K / MRR / NDCG）、**训练价值**（代写率、错因 Top-K）、**工程可用性**（分层架构、OpenAPI 全量 28 路径/32 端点 + 19 个演示接口的三角色权限矩阵、append-only 审计、P95 延迟、容器化与 CI）。 | 全部指标有脚本产出，结论进论文表格，非"感觉更快更准"。 |

### 1.3 凭什么算"优秀毕设"（三条判定）

1. **有基线、有对照、有增量**：v3 是完整可运行基线（77 条、38 单测、A/B 实验台），v4 的每一项改造都能对应"改造前 vs 改造后"的数据对比，而不是从零堆功能。
2. **技术动作落在软件工程主干上**：分层架构与仓储层、鉴权与审计、可观测性、容器化与 CI、测试分层——这些是软件工程专业评审最认的"工程规范性"，而混合检索与消融实验提供"技术难度"。
3. **范围可控、里程碑可验证**：三期路线图中每个阶段都有可出示的产物（报告/表格/镜像/测试报告），避免"永远在建、答辩时只有 Demo"。

**三处路径以代码为准（此前写法指向不存在的接口，评委对代码一查就露）**：`/auth/refresh` → **已删除**（团队裁决单 access token 2h，不做 refresh），改为 `/auth/password` 改密；`/retrieval/config` → `/api/v1/ops/config`；`/health` → **`/healthz`**（`/version` 单列且仅 admin）。

**角色定稿**：`student` / `admin` / `auditor`。**不设"教师/助教"独立角色**——教师以 `admin` 或 `auditor` 身份使用。第三角色的价值不是"多一个人"，而是"多一道制约"：`auditor` 纯只读、无任何写权限，`admin` 的操作有人可查、查的人改不了数据（职责分离）。

**四条安全硬约束**（答辩被问"你的接口有什么风险"时直接答）：
1. `POST /knowledge/import` 只给 `admin` —— 它是唯一批量写入口，一次可改上千条，风险等级高于单条 CRUD，须落 `KB_IMPORT` 审计（二次确认**设计上建议、本版未实现**，不要现场说"有二次确认"）。
2. `GET /api/v1/ops/config` **默认不注册路由**（`ENABLE_DEBUG_API=false` 时整条路由不存在，而非返回 403）；开启时仅返回白名单标量字段（实际返回以 `api/routers/ops.py::config_view` 为准：`top_k / recall_k / rrf_k / bm25_k1 / bm25_b / strong_threshold / weak_threshold / enable_rerank / embed_model / embed_text_mode / type_boost / enable_bm25_field_boost / bm25_title_weight / bm25_tags_weight / rerank_max_length / rerank_cache_size`），**禁止返回任何路径、密钥、服务地址、集合名**。
3. `GET /healthz` 只返回 `{"status":"ok"}`，**不查依赖、不暴露版本号/依赖清单/Python 版本**（版本走 `/version`，仅 admin）。2026-11-21 起索引与模型改后台线程预热，`/healthz` 约 1s 即返回（此前需 15.7s）；真正等索引就绪用 `/readyz`，其响应含 `warmup: {started, index_done, reranker_done}`，未就绪返回 503。首个检索请求若早于预热完成，会在 `HybridRetriever` 的加载锁上等待，不会拿到半加载索引（由 `tests/test_startup.py` 锁定）。`/metrics` 与 `/version` 均为 `StaffUser` 鉴权（**仅 `admin`/`auditor` 可读**），**不进学生可见的统计页**。
4. **审计入库 + append-only，但要说准实现层级**：`audit_logs`（复数）在**应用层已成立**——`AuditRepository` 只有 `write()` 与 `recent()`，**没有任何 update/delete 入口**；**DB 层触发器已实现**（`db/session.py` 的 `audit_logs_no_update` / `audit_logs_no_delete`，两条 `RAISE(ABORT)`），答辩表述为"应用层无删除入口 + DB 触发器兜底"，**不要说"已有哈希链"**（哈希链属可裁剪项）。`result` 取值 `ok | denied | error`（403 记 `denied`）。`username` 列**可空、写入时传 `None`**（审计只用 `user_id`，不记用户名）。**11 类必录事件**：`AUTH_LOGIN_SUCCESS`、`AUTH_LOGIN_FAIL`、`AUTH_LOCKED`、`AUTH_PASSWORD_CHANGE`、`ACCESS_DENIED`、`KB_CREATE`/`KB_UPDATE`/`KB_DELETE`（分开录）、`KB_IMPORT`、`DIAG_RUN`、`EXPORT_DATA`、`ADMIN_ROLE_CHANGE`。选录标准一句话：**"要么能造成数据外流，要么能改变权限，要么能掩盖前两者"**。`QUERY_ASK`/`RETRIEVE`/`GENERATE` 高频低风险 trace **不入库**，落 `logs/trace.jsonl`。

> 约定（设计基线）：业务接口在 `/api/v1` 前缀下；分页设计为 `page/page_size`、错误体设计为 `{code, message, request_id}`。**落地实现以代码为准**：分页为 `page/size`（`schemas.py::PageResponse`），错误体为 `{code, message, trace_id, details}`（`api/app.py` 的异常处理器）。

## 三、创新点提炼（技术动作 + 对比基线 + 量化指标）

> 本科毕设层面的"创新"应表述为**组合创新 + 工程增量 + 可量化验证**，答辩时主动把"哪些是自研、哪些是复用"讲清楚，比硬说首创更稳。

### 创新点 1：稀疏—稠密双通道检索与 RRF 融合，解决短查询长文档的长尾召回

| 项 | 内容 |
|---|---|
| **技术动作** | ①自研 BM25 倒排索引（可配 k1/b、jieba 自定义词典 + 代码标识符驼峰/下划线切分、字段加权 title×3 / tags×2 / body×1）；②稠密通道用 `bge-small-zh-v1.5`（512 维，本地）与 Chroma 封装；③两通道分数经 **RRF** 融合，不直接加权求和（跨量纲不可比）——**k 值取 60 为初始值，最终值由 k∈{10,20,60,100} 敏感性实验确定**（只测 30/60/100 会因三者差异通常 <2pp 得出"k 不敏感"的弱结论，加 k=10 才有区分度）；④融合后 `bge-reranker-base` cross-encoder 精排 Top-30→Top-5。 |
| **对比基线** | v3：Chroma 向量 top-k=4，无稀疏通道。**必须报两套基线**：**B1 纯召回**（跳过三闸，取向量 top-10，用作消融分母）与 **B2 线上行为**（完整三闸，含 `best_distance>0.68` 直接返回空的行为）。**不可混用**——v3 的 `retrieval_eval.py` 测的是 B2（最终递给 LLM 的列表），拿它当消融分母会让 BM25/重排的增益被拒答闸门污染。**双跑前必须先解决一个坑**：v3 加 `--no-gate` 开关（约 15 行，`rag.py` 一行不改，直接 `collection.query(n_results=10)` 绕过 `_select_relevant`），v4 用 `eval --gate off`，**B1 对比两边都关闸、B2 对照两边都开闸**，否则 77 条语料上相当比例的 query 会被 v3 拒答成空、数字不可比。qrels 走 `qrels_source.jsonl` 单一真源导出两份，v3 读 legacy 格式 `{"query","expect":[...]}`，**legacy 的 `expect` 必须用原始 title、不能归一化**（`01背包` 若被 norm 成 `01 knapsack`，v3 子串匹配全 miss）。**两条 77 条双跑的解读纪律**：①BM25 的 IDF 在 N=77 时不稳定，**77 条上的 Hybrid 数字只用于"结构等价性验证"，不能用来论证 BM25 的价值**（BM25 价值须在 8,500 档论证）；**`--gate off` 必须同时置空 `max_distance` / `weak_distance`**——只关判定逻辑却保留距离参数，会得到**既非 B1 也非 B2 的第三种口径**，结果看起来"正常"（有召回、有指标）却与任何基线不可比，这种错误最难发现。**还有一条混比禁令**：v3 关闸后的 `RAG_MAX_DISTANCE=0.80` 是 **L2 距离**，v4 的 `strong_threshold` 是 **cosine 相似度**，两者不是同一口径——**B2 对比必须两边都关闸或都按各自默认，严禁"v3 开闸 vs v4 关闸"混比**，这种混比做出来的提升最容易被一票否决。 |
| **量化指标** | **口径**：同一台机器、同一份 77 条语料、同一批 test 集上，v3 与 v4 双跑；冻结产物为 `experiments/results/baseline_v3.json`，字段含 `n / Recall@5 / Recall@10 / MRR@10 / NDCG@10 / P@5 / 空结果率`（**空结果率必须单列**——v3 在 77 条库上的拒答行为本身是有价值的结论）。v3 实测值 **P0 期末冻结、不预设**。**目标值**（待第 5 章实验回填）：B1 口径下 Hit@5 ≥0.90、MRR@10 ≥0.75、NDCG@10 ≥0.80；**检索 P95 ≤300ms**（实测预期 80–200ms，**需模型预热**，冷启动不计入）、**含重排 P95 ≤800ms（CPU）**——**重排延迟必须连口径一起写**：30 条 batch 总耗时、文档截断 384 token、top_n 固定 24、**CPU 单核与 GPU 分报**（预估 CPU 350–500ms、GPU 30–60ms）；只给数字不给口径，答辩必被追问。若把 top_n 从 24 降到 20 则目标 ≤600ms。**端到端首 token 目标 2.5s**（检索段 ≤0.8s + LLM 首 token ≤1.7s，受外部网络影响，**写目标值不写承诺**）。子集结论**双重有条件**：T3 标识符型 Hit@5 提升 ≥25pp 需 ①**T3 ≥50 条**（n=30 时 CI 半宽约 ±14pp，n<30 只写"显著优于基线"不写 pp）②**在 8,500 条语料上做**（77 条里每个 tag 仅 2–3 条，BM25 与向量都能召回，差不出 25pp）；若实测只有 +8pp 就如实报——**负结果比拔高安全**。 |
| **验证方式** | **评测集总量 300 = 标定/dev 150（主集 100〔易 50 / 中 50〕+ 拒答集 50〔难 40 / 超纲 10〕）+ test 150**。**标定集与 test 集必须分离（防数据窥探）**：标定集用于定 `T_strong`（需主集 100 支撑 precision≥0.9）与 `T_none`（需拒答集 50），test 集只用于报指标；test 150 时 95% CI 半宽 ≈±6.4pp。**降级规则**：若压到 250，则标定集降为 100（主集 70 + 拒答 30），`T_strong` 的 CI 放宽到 ±8pp 并在论文注明；若压到总 150（test 仅 90），只报整体指标、删掉全部子集结论。**qrels 双向构造（与 curated 条数解耦，勿用"精讲条数 ×2.5"推算配额）**：一半由**全量 8,558 条语料**自动生成（标题问法 / 标签问法 / 代码信号问法），一半取自真实学生会话日志；人工只做 0/1/2 相关性判定，一致性报 **κ≥0.7 或一致率 ≥85%**。**`query_type` 判定流程（有方法论陷阱，别说错）**：生成方式 ≠ query_type——"标题/标签/代码信号问法"是**制造 query 的手段**，`query_type` 是**语言形态**；**必须先生成 query、再按形态判定 T1–T4**，不得按生成方式直接赋值（否则"标签问法→identifier"会造成分桶系统性偏移）。**分层规则（互斥，命中即定层，按优先级）**：T4 题号型（`CF\d{4}` / `ABC\d{3}`）→ T3 标识符型（算法缩写 LIS/KMP/DP、函数变量名 `lower_bound`/`dp[j]`、题名片段）→ T2 报错型（TLE/WA/RE/MLE/死循环/超时/段错误）→ T1 概念型（其余）。**分桶配额（生成阶段反向控制，不能事后统计）**：concept ≥30、error ≥30、**identifier ≥50**、problem_id ≥30；自动池 75 条里主动多造 identifier（代码信号问法 20 + 标签缩写问法 20）。**消融矩阵只保留 G1–G4 在 test 全集上报**（G1 Vector only / G2 BM25 only / G3 Hybrid-RRF / G4 Hybrid+Rerank）；**G5 查询改写、G6 元数据先验作为子集实验单独报**（改写只对追问子集生效，n≈40–50，放全集会稀释到 +1~2pp、归因不清）。**`query_type` 三条实现纪律**：①**禁止用 LLM 判类型**（不可复现，同一 query 两次跑出两个类型没法解释），用规则脚本（正则按 T4→T3→T2→T1 顺序匹配、命中即 break）；②**判定结果必须落盘可查**——每条 query 在 `qrels_source.jsonl` 里带 `query_type` + `matched_rule`（命中的是哪条正则），答辩问"你怎么分类的"直接展示规则表 + 匹配证据；③**人工复核 10–15%**，重点查 T3（正则最易误伤，如 "DP" 可能是"DP 值"不是动态规划）。**责任主体**：判定规格由 kb-retrieval-tuner 提供（`04` §6.1.3），脚本实现与运行挂主研（S2 交付"qrels 构建脚本 + 50 条试标报告"），抽检由 tuner 负责。**实现状态**：`scripts/eval_retrieval.py --config {g1..g6}` **计划 P1 阶段实现**，实现后具备一键复现能力——**当前不具备，不得表述为"已可一键跑出"**。 |

### 3.5 指标口径与看板（答辩被问"你的指标怎么算"时的口径表）

> 口径说明：本表定义的是**怎么算**，不是**算出多少**。所有数值目标见 §3 各创新点，实测值统一待第 5 章回填；下表不含任何预设数值。**所有检索指标分 B1（纯召回）/ B2（线上行为含三闸）两套口径分别报，禁止混用**（详见创新点 1）。

| 指标 | 类型 | 定义 | 采集方式 |
|---|---|---|---|
| Hit@1 / Hit@3 / Hit@5 | 领先（质量） | test 集（150 条）中，qrels 判定为 2（完全相关）的条目出现在 Top-K 的比例 | 离线脚本 |
| MRR@10 | 领先（质量） | 首个相关性 ≥1 的条目排名倒数的均值 | 离线脚本 |
| **NDCG@10** | 领先（质量） | 按相关性等级（0/1/2）与位置折损累计的归一化增益，能区分"部分相关" | 离线脚本 |
| **真拒答率** | 领先（供给） | B2 空结果中「77 条库里**确实没有**能回答的条目」的占比 → **扩库动机（立论）**，放论文问题定义章 | 抽 50 条人工判定有无 |
| **假拒答率** | 领先（阈值） | B2 空结果中「库里有相关条目但被三闸 `best_distance>0.68` **误拒**」的占比 → **v4 阈值须按分位数重标的证据**，放动机/方法章 | 同上 |
| 代写率 A/B/C | 领先（行为） | 输出可直接提交的完整代码的题目占比 | 实验台 + Judge |
| 错因 Top-K | 领先（质量） | 诊断结果 Top-K 命中人工标注错因 | 40 份标注集 |
| 检索 p95 / 生成首 token p95 | 过程（性能） | 分阶段埋点耗时 | Prometheus 直方图 |
| 日活 / 人均有效会话 | 领先（使用） | 有 ≥3 轮对话的会话数 | 埋点 |
| 满意度 / 引导有效性 | 滞后（价值） | 5 分制评分 + "看提示后自行 AC"问卷 | 站内评分 + 问卷 |
| 知识条目新鲜度 | 过程（治理） | 90 天内更新的条目占比 | `knowledge.updated_at` |

**NDCG@10 的五条实现约定**（来自 `04` §6.2.1，v3/v4 必须逐条一致，否则同一次运行会算出两个数——这是最容易出分歧的指标）：

| # | 约定 | 为什么关键 |
|---|---|---|
| ① | 结果不足 10 条**补 0**，不是截断后重算 IDCG | 最易分歧点 |
| ② | IDCG 候选来自"该 query **全部标注条目**"，不是检索结果里出现的 | 多数 query 只有 1 条 gold → IDCG=3 |
| ③ | `gain = 2^rel − 1` → rel 0/1/2 得 **0/1/3**（指数）；若用线性 `gain=rel` 得 0/1/2，**两者结果不同** | 两种都合法，但必须两边一致 + 论文写明用哪种，**推荐指数** |
| ④ | `discount = log2(rank+1)`（rank 从 1 起） | 统一用 rank 从 1 起不易错 |
| ⑤ | 空结果（三闸拒答）→ NDCG=0，**同时单独计入空结果率** | 防止空列表被静默剔除、虚高 |

> 为什么必须有 NDCG：query"01 背包遍历方向"，第 1 名是全背包（rel=1）、第 2 名是 01 背包（rel=2）→ **Hit@1=0 但 NDCG@10≈0.79**。G3/G4 的差异主要就体现在这类"第 1 名是 rel=1"的样本上，所以 NDCG 是消融表的关键列，不能省。

> **空结果率必须拆成两个数，不能合并报**（合并成一个"空结果率 40%"既不能证明扩库必要、也不能证明阈值有问题，只剩一个负面印象）：从 B2 的空结果里抽 50 条，人工只判断"77 条库里是否真的存在能回答的条目"（不判好坏、只判有无，约 1 小时）。若真拒答占 80%+ → 写"v3 对 X% 的查询无法给出依据，其中 85% 是题库确实未覆盖，这正是扩库的直接动因"；若假拒答占 30%+ → 写"固定距离阈值导致 X% 的可回答查询被误拒，这是 v4 改分位数标定的依据"。**两个都写**，因为它们论证的是两件事；并**按难度分层报**（77 条库几乎全是易/中题，困难查询必然空，分层表本身就是扩库最硬的证据）。

> **延迟数据的测量条件**（必须随表给脚注，否则同数换台机器复现不了）：**CPU 单机（6 线程 / torch 2.15.0+cpu / 无 GPU）、模型已预热、`top_n=24`（生产）或 100（消融，为支撑 Recall@100）、`RERANK_MAX_LENGTH=192`（2026-11-21 优化后；优化前为 512）**；GPU 环境另报。重排耗时对 `max_length` 极敏感（24 对下 512→192 从 8.2s 降到 2.9s），且不标 `top_n` 无法复现。消融表 G4 的 8.5s 是**优化前 + top_n=100** 口径，答辩须说明这是历史值；优化后生产冷启动 2.85s、缓存命中 14ms（见 docs/04 §3.2）。

**北极星指标**：`有效引导会话数 = 有 ≥3 轮对话且未触发代写拒答上限的会话数`——一个指标同时反映质量、行为约束与真实使用。

## 七、答辩问答预案（12 道主题 + 2 道备用，共 14 题，回答控制在 3 句内）

| # | 评委可能追问 | 回答要点（≤3 句） | 备用证据 |
|---|---|---|---|
| 1 | **为什么不用 LangChain / LlamaIndex？** | 本系统链路只有"召回—融合—重排—约束生成"四段，LangChain 的抽象层会隐藏 token 预算与通道分数，而我的实验恰恰要观测每个通道的贡献。自研约 900 行，换来消融可解释性与零版本漂移风险。评测与部署依赖也更少（依赖树从数十个降到 8 个核心包）。 | ADR-03《不用 LangChain 的理由》；`requirements.txt` 依赖数对比；消融脚本引用 |
| 2 | **为什么自己写 BM25 而不用 rank_bm25？** | 需要现成库不直接给的三件能力：字段加权、中英混合分词（代码标识符切分）、单通道分数直接进 RRF；另有可解释性与避免重依赖的考虑。自研约 220 行，正确性用**与 `rank_bm25.BM25Okapi` 官方实现逐条对拍**验证：1000 组抽样查询**最大绝对误差 <1e-6、Top-10 排序完全一致**（浮点累加顺序决定不可能有严格 0 误差，报告里不写 0）。当前语料约 **2 万 chunk**（8,500 题 × 2–3 片），建索引 **30–60 秒**（jieba 分词为主要成本）。 | `tests/test_bm25.py` 对拍用例；倒排建索引耗时与内存实测表 |
| 3 | **8,500 条比 77 条，效果上有什么实质提升？** | v3 对 75 个知识点覆盖 **74.7%**，但 **19 个零覆盖、39 个仅 1 条支撑（52%）**——`constructive algorithms`（CF 实测 **2,153** 题）在 v3 就是 **0 条**，这类问题系统只能拒答。扩到 8,500 后按**分层指标**补（高频 ≥50、长尾 ≥5 且必有精讲），把单点支撑率压下来。真正的难点不在抓取量而在数据工程：**CF 全库 43.8% 是 ≥2000 的困难题、v3 困难题仅 19.5%**，直接全量入库会让语料难度上移、基础题被挤出召回位，必须按 rating 分层采样 + 去重 + 标签归一。 | CF API 实测（2026-11-07）：全库 11,503 题、34/38 tag 可达 30 条；四段漏斗计数表；75 知识点覆盖矩阵（74.7% / 52%） |
| 4 | **RRF 的 k=60 怎么定的？为什么不做加权求和？** | 两个通道分数量纲不同（余弦距离 vs BM25 分数），加权求和需每次重新标定，RRF 只用排名因而稳定；k=60 取文献常用值作为初始值。敏感性实验设计为 **k∈{10,20,60,100}**（只测 30/60/100 会因三者通常差 <2pp 得出"k 不敏感"的弱结论，加 k=10 才有区分度），**已排入实验章节第 6 组、计划 P2 期完成**，最终 k 值按实测确定。 | 敏感性实验表（4 行）；`docs/ADR-04` |
| 5 | **cross-encoder 重排的延迟代价值得吗？** | 重排只作用于融合后的 Top-24（可降到 20）：**24 条 batch 总耗时、文档截断 384 token、top_n=24，CPU 单核 350–500ms、GPU 30–60ms（分开报）**，含重排的检索段 P95 目标 ≤800ms；端到端首 token 目标 2.5s（检索 0.8s + LLM 1.7s），属需实测的目标值。收益是 MRR@10 与 NDCG@10 的提升（**G4 vs G3**，数值待实验回填）——第 1 名是 rel=1、第 2 名是 rel=2 的样本正是重排起作用的场景；可一键关闭（`RERANK_ENABLED=false`）走融合打分兜底。 | G4/G3 对比行；延迟分解柱状图（含口径标注） |
